Three defaults change in this release (templateFailureAsServerError, maxLoggedMatchFailures, matchBinaryExpectationsWhenProxying), each with an opt-out, plus stricter statusCode validation, which has no opt-out — see Upgrading to MockServer 9.1.0 for what changed and how to keep the old behaviour.

 

Common configurations

Copy-paste one of these blocks as a starting point. All values can be overridden by system properties or environment variables at runtime.

Local development

Low memory footprint, verbose logs, CORS enabled for browser-based testing:

# mockserver.properties — local dev
mockserver.devMode=true
mockserver.logLevel=DEBUG
mockserver.enableCORSForAPI=true
mockserver.enableCORSForAllResponses=true

Or with Docker:

docker run -d --rm -p 1080:1080 \
  -e MOCKSERVER_DEV_MODE=true \
  -e MOCKSERVER_LOG_LEVEL=DEBUG \
  -e MOCKSERVER_ENABLE_CORS_FOR_API=true \
  -e MOCKSERVER_ENABLE_CORS_FOR_ALL_RESPONSES=true \
  mockserver/mockserver

CI (shared, parallel test runs)

Cap memory so multiple MockServer instances can run on the same CI node, load expectations from a JSON file, and reduce log noise:

# mockserver.properties — CI
mockserver.logLevel=WARN
mockserver.maxExpectations=1024
mockserver.maxLogEntries=4096
mockserver.initializationJsonPath=/ci/expectations.json

Production / shared team instance

Higher limits, metrics enabled, CORS off, TLS enforced (supply your own certificates):

# mockserver.properties — production
mockserver.logLevel=INFO
mockserver.maxExpectations=16384
mockserver.maxLogEntries=65536
mockserver.metricsEnabled=true
mockserver.enableCORSForAPI=false
mockserver.enableCORSForAllResponses=false

Settings Properties

Note: configuration properties loaded from property files and environment variables are read once at startup and cached. Changes to property files or environment variables after MockServer has started will not take effect. To change configuration at runtime, use the REST API (PUT /mockserver/configuration) or programmatic ConfigurationProperties method calls. System property changes via ConfigurationProperties static methods are read dynamically for properties that support runtime changes (e.g., logLevel).

What you can rely on with PUT /mockserver/configuration: changes take effect for request handling immediately, however MockServer was started — command line, Docker, the Maven plugin, ClientAndServer, the JUnit integrations, or Spring. If the request changes authentication or TLS settings, those switch over all at once — there is no moment where part of the change has applied and part has not. If a request is rejected (for example an invalid certificate path, or a negative value for a setting that must not be negative), it answers 400 and leaves the configuration exactly as it was before the request.

See also: Chaos Testing & Fault Injection for injecting errors, latency, and outages into mocked and proxied responses using declarative chaos profiles.

Properties can be set by:

  1. java code (highest precedence)
  2. @MockServerTest annotation (per-instance Configuration object)
  3. system property
  4. property file
  5. environment variable (lowest precedence)

Each level overrides the levels below it. For example, a system property overrides the same key in a property file, which in turn overrides an environment variable.

When using @MockServerTest, properties prefixed with mockserver. (e.g. mockserver.initializationClass=...) are applied to the per-instance Configuration object, not to global system properties. This makes them safe for parallel test execution.

Some properties need to be set before MockServer starts because they are only read at start-up, for example, nioEventLoopThreadCount.

Other values are read continuously and so can be changed at any time, for example, logLevel.

 

Programmatic Properties

There are two ways to set properties programmatically, as follows:

  • org.mockserver.configuration.ConfigurationProperties
    • is JVM global
    • exposes static methods
    • stores property values in system properties
  • org.mockserver.configuration.Configuration
    • is unique to each MockServer instance
    • can be passed to ClientAndServer, MockServer and MockServerClient classes
    • only supports instance methods
    • defaults to ConfigurationProperties for unset values
 

Property File

The property file defaults to filename mockserver.properties in the current working directory of MockServer.

This location of the property file can be changed by setting the mockserver.propertyFile system property or MOCKSERVER_PROPERTY_FILE environment property, for example:

-Dmockserver.propertyFile=/config/mockserver.properties

A full example / template properties file can be found in github

An limited properties file example is, as follows:

###############################
# MockServer & Proxy Settings #
###############################

# Socket & Port Settings

# socket timeout in milliseconds (default 20000)
mockserver.maxSocketTimeout=20000

# Certificate Generation

# dynamically generated CA key pair (if they don't already exist in specified directory)
mockserver.dynamicallyCreateCertificateAuthorityCertificate=true
# save dynamically generated CA key pair in working directory
mockserver.directoryToSaveDynamicSSLCertificate=.
# certificate domain name (default "localhost")
mockserver.sslCertificateDomainName=localhost
# comma separated list of ip addresses for Subject Alternative Name domain names (default empty list)
mockserver.sslSubjectAlternativeNameDomains=www.example.com,www.another.com
# comma separated list of ip addresses for Subject Alternative Name ips (default empty list)
mockserver.sslSubjectAlternativeNameIps=127.0.0.1
# maximum number of dynamically-discovered SANs the auto-generated certificate will accumulate (default 100)
mockserver.maxSubjectAlternativeNames=100
# number of days the auto-generated leaf certificate is valid for (default 397)
mockserver.sslCertificateLeafValidityInDays=397

# CORS (both default to false; set to true to enable)

# enable CORS for MockServer REST API
mockserver.enableCORSForAPI=true
# enable CORS for all responses
mockserver.enableCORSForAllResponses=true
 

JSON Configuration File

MockServer also supports configuration via a JSON file. To use a JSON configuration file, set the mockserver.propertyFile system property or MOCKSERVER_PROPERTY_FILE environment variable to a file path ending with .json, for example:

-Dmockserver.propertyFile=/config/mockserver.json

The JSON format uses camelCase property names without the mockserver. prefix. An example JSON configuration file:

{
  "logLevel": "INFO",
  "maxSocketTimeout": 120000,
  "dynamicallyCreateCertificateAuthorityCertificate": true,
  "directoryToSaveDynamicSSLCertificate": ".",
  "sslCertificateDomainName": "localhost",
  "sslSubjectAlternativeNameDomains": ["www.example.com", "www.another.com"],
  "sslSubjectAlternativeNameIps": ["127.0.0.1"],
  "maxSubjectAlternativeNames": 100,
  "sslCertificateLeafValidityInDays": 397,
  "enableCORSForAPI": true,
  "enableCORSForAllResponses": true
}

Note: enableCORSForAPI and enableCORSForAllResponses both default to false. The examples above set them to true to illustrate enabling CORS. They govern mocked and proxied responses. Whatever they are set to, MockServer's own API only answers web pages on localhost or served by MockServer itself, unless controlPlaneCorsAllowOrigin names another origin (see which web pages can use MockServer's own API).

The JSON property names are the camelCase equivalents of the mockserver.* property names listed below, with the mockserver. prefix removed. For example, mockserver.maxExpectations becomes maxExpectations in JSON. The complete list of supported JSON keys can be obtained by calling GET /mockserver/configuration, which returns all properties with their current values, except credentials (see below). This output can be saved as a JSON configuration file and reloaded at startup.

Credentials are never read back. Properties that hold a secret — passwords, bearer tokens, API keys, private keys, cloud access keys and connection strings, such as proxyAuthenticationPassword, dataPlaneBearerAuthenticationToken, clusterFanInPeerAuthToken, llmApiKey and blobStoreSecretAccessKey — are write-only: you can set them with PUT /mockserver/configuration, but GET /mockserver/configuration either omits them or returns ***REDACTED*** in their place, so anyone who can read the configuration cannot lift a credential from it. This means the saved output does not contain the credentials MockServer holds, and that taking the output of a GET and sending it straight back with a PUT leaves the credentials MockServer already holds untouched — but also that a configuration file produced this way needs its credentials supplied again (by property, environment variable or a later PUT) when used to configure a fresh instance.

Five properties come back masked rather than omitted, so you can read and edit the rest of the configuration around them. They fall into two groups, and the editing rule differs between them.

Whole-value credentials — replace the entire mask. llmApiKey, prometheusRemoteWriteBearerToken and prometheusRemoteWriteBasicAuthPassword come back as nothing but ***REDACTED***, because the whole value is the secret. To change one, type the new secret on its own in place of the entire ***REDACTED*** — do not type text next to the mask. A value that still contains ***REDACTED*** anywhere in it (for example sk-***REDACTED***) is not a credential MockServer can use, so it is ignored and a warning is logged, leaving the credential already in force unchanged. Sending the mask back untouched is the normal round trip: it changes nothing and logs nothing. Setting the value to an empty string still clears the credential.

Credentials inside a value — leave the masks you are not changing exactly as they came back. prometheusRemoteWriteHeaders is masked one header at a time and llmBackendsConfig one credential-named field at a time (apiKey, token, secret, password and similar), so the headers and backends around the secret stay readable. Sending such a value back containing ***REDACTED*** is the supported edit, not an error: MockServer puts the real secret back into each untouched mask and applies everything you did change. So to rename a header, add one, or change X-Scope-OrgID from tenant-a to tenant-b, edit just that part and leave Api-Key=***REDACTED*** as it is — never paste the real secret back in to work around the mask. To rotate a secret, type the new one on its own in place of that item's whole ***REDACTED***. A mask with text welded onto it (for example Api-Key=***REDACTED***-new, Authorization=Bearer ***REDACTED***) leaves MockServer unable to tell which secret you meant; it then applies none of that value and logs a warning saying so.

Do not copy a ***REDACTED*** out of GET /mockserver/config or --print-config into a PUT body. Those two outputs (and the dashboard's Server Info tab) mask every credential-named property, but most of those properties — proxyAuthenticationPassword, dataPlaneBearerAuthenticationToken, clusterFanInPeerAuthToken, blobStoreSecretAccessKey, privateKeyPath and the rest — are not returned masked by GET /mockserver/configuration at all, so a ***REDACTED*** arriving for one of them did not come from a round trip of the endpoint you are writing to. MockServer will not store it: it keeps the credential it already holds, logs a warning naming the property so a PUT that wrote nothing does not simply answer 200 OK in silence, and applies every other change in the same body normally. Set those properties to their real value, or to an empty value to remove one.

 

Checking The Configuration In Use

To see the value MockServer is using for every property, and where each value came from (a system property, the properties file, an environment variable, a value set in Java code, or the built-in default), run MockServer with --print-config, call GET /mockserver/config, ask an AI assistant to use the MCP diagnose_config tool, or open the dashboard's Server Info tab. A property at its built-in default shows that default's value; a default worked out from the JVM heap size (such as maxLogEntries) or from another property shows the value worked out now. A property you have changed also shows the built-in default it replaced: --print-config ends its line with (default: ...), GET /mockserver/config and diagnose_config add a default field, and the Server Info tab shows it beside the value. A credential's default is always shown as ***REDACTED***. Credentials (passwords, tokens, API keys, private keys and other secrets) are always shown as ***REDACTED***. To list only what differs from the built-in defaults — the settings you have actually changed — call GET /mockserver/config?nonDefault=true.

Misspelt properties. A mockserver.* system property or properties-file key, or a MOCKSERVER_* environment variable, that is not a known property is ignored. MockServer logs a warning at startup naming it and, when a known property is close enough to be what you meant, names that property in the same form you used, for example:

unrecognised MockServer configuration environment variable [MOCKSERVER_METRICS_ENABLE] - it is not a known configuration property and will be ignored (did you mean MOCKSERVER_METRICS_ENABLED?)

A name that differs from a known property only in case or separators, such as mockserver.max_expectations or MOCKSERVER_MAXEXPECTATIONS, is matched too. The same keys appear at the end of --print-config, in GET /mockserver/config (with the source unrecognised), under unrecognised in the MCP diagnose_config tool's answer and under Unrecognised (ignored) in the Server Info tab. Defaults that change in a future major release. Four groups of defaults are expected to change to safer values in a future major release: forwardProxyBlockPrivateNetworks (to true), localBoundIP (to 127.0.0.1), attemptToProxyIfNoMatchingExpectation (to false) and the HTTP parsing limits maxInitialLineLength, maxHeaderSize and maxChunkSize (to 8192, 16384 and 16384 bytes). While one of these is not set, MockServer logs a warning at startup (once, whichever server in the JVM starts first) saying what will change and how to keep the current behaviour. Set the property to the value you want (either value for the three switches, any value for the limits); that also removes its warning.

Developer Mode:

When enabled, applies a developer-friendly configuration profile that reduces memory usage for laptop and test-suite workloads. The following defaults are overridden (only for properties the user has not explicitly set via system property, environment variable, or properties file):

  • maxLogEntries is set to 1,000 (instead of the heap-based default up to 250,000)
  • maxExpectations is set to 1,000 (instead of the heap-based default up to 15,000)

This is useful when running MockServer locally during development, where retaining tens of thousands of log entries is unnecessary and wastes memory.

Enabled by default under the JUnit integrations. The JUnit 4 rule (MockServerRule) and the JUnit 5 extension (MockServerExtension) turn dev mode on by default, because a test suite that starts many short-lived MockServer instances in one JVM benefits most from the smaller, deterministic footprint (a measured ~117 MB down to ~52 MB across 32 in-JVM instances). The practical consequence is the 1,000-entry log cap: if a single test records more than 1,000 log entries against one MockServer instance, the oldest are overwritten, so a verify that reaches back past the most recent 1,000 entries can stop matching. When dev mode is in effect MockServer logs a one-time INFO line naming the effective sizes and how to change them. To keep the old behaviour under JUnit, either raise the caps explicitly (-Dmockserver.maxLogEntries=… / -Dmockserver.maxExpectations=…, which win over the dev-mode default) or turn dev mode off with -Dmockserver.devMode=false (or MOCKSERVER_DEV_MODE=false). An explicit setting always beats the default. The Spring test integration and a directly-constructed ClientAndServer do not turn dev mode on themselves — for those it stays off unless you enable it. One caveat if you mix them in the same JVM: enabling dev mode is global, so once a JUnit rule or extension has run in a test fork, a ClientAndServer constructed directly afterwards in that same fork inherits the dev-mode store sizes too (unless it sets its own).

Memory Usage Configuration:

Maximum number of expectations held in the in-memory ring buffer. Expectations are stored in a circular queue so once this limit is reached the oldest and lowest priority expectations are overwritten.

Type: int Default: minimum of (JVM heap size in KB / 10) and 15000

The default is calculated automatically from the JVM heap size (the -Xmx maximum), so it is the same for every MockServer instance in a JVM and does not depend on how much memory happens to be in use when the first instance starts. Each expectation typically uses 4-10 KB of heap for small response bodies. Expectations with large response bodies use significantly more: a 10 KB response body results in ~15-20 KB per expectation, a 50 KB response body results in ~55-75 KB per expectation. With a 256 MB heap, the default is approximately 15,000. You can override this if you need more or want to reduce memory usage. On JVMs that do not report a usable heap maximum (for example GraalVM native images), the default falls back to a floor of 1,000 — set the property explicitly to override.

Power-of-2 sizing: the ring buffer is implemented on top of the LMAX Disruptor, which rounds the configured size up to the next power of 2. Setting maxExpectations=10000 actually allocates 16,384 slots (a 63.8% overhead). To minimise wasted heap, pick a power-of-2 value yourself: 1,024 / 2,048 / 4,096 / 8,192 / 16,384 / 32,768 / 65,536.

Number of slots in the in-memory log event ring buffer. This buffer holds log events briefly while they are passed from the threads handling requests to the single thread that writes them to the log — it is not the retained log history (that is controlled separately by maxLogEntries). The ring buffer only needs to absorb short bursts of log events, so it can be much smaller than the retained history.

Type: int Default: minimum of maxLogEntries and 16,384 (rounded up to the next power of 2)

Raising this absorbs a short burst of small log entries without dropping them — it gives the consumer thread more room to catch up once the burst ends. It does not help against sustained drops at a verbose log level, where entries arrive faster than one thread can ever drain them (see below); for that, lower the log level instead, or keep INFO and set maxLoggedMatchFailures. Lower ringBufferSize to save a little memory on a workload that retains a lot of history but receives requests slowly. The value is rounded up to the next power of 2 because the underlying LMAX Disruptor requires it.

At logLevel INFO, one thread renders every log entry, and on a busy server that thread is the more likely bottleneck, not this buffer's size. In our own load tests we estimate that thread falls behind and starts dropping entries from roughly 8,000–10,000 requests/second on a 6-core server with four expectations, where the request matches the last one (about six log entries per request). Each expectation checked before a match adds another entry, so with more expectations drops start at a lower rate — roughly half as many requests per second with ten (again matching the last one). Raising ringBufferSize delays this but does not remove it, because the entries still accumulate faster than one thread can render them. For a high-throughput workload that calls verify, prefer running at WARN or ERROR (see Log Level), which skips the per-expectation diagnostic entries that saturate this thread. To keep INFO, set maxLoggedMatchFailures (for example to 10) instead: it caps how many of those entries each request writes. A once-only WARN (“Log event ring buffer full — dropping log events…”) naming both remedies is logged the first time this happens after each reset regardless of metricsEnabled, unless logging or system-out is disabled. You can also watch for drops with metricsEnabled set to true — the mock_server_dropped_log_events counter, which counts these drops under the label reason="ring_full", and the dashboard's log-pressure banner, which says which kind of drop happened and what to change, both need it, and show nothing while it is off (the default).

Previously the ring buffer was sized from maxLogEntries, so a large retention setting (e.g. maxLogEntries=250000) forced a 262,144-slot ring (~29 MB of pre-allocated, mostly-empty slots). The default 16,384 ceiling caps that overhead while leaving small deployments unchanged.

OOM guard for the in-memory event log. Entry count (maxLogEntries) alone cannot protect a memory-constrained server, because a count cap treats a 10 MB body the same as a 10-byte one — so a few thousand large request/response bodies (e.g. LLM tool schemas, growing conversation context, or accumulated SSE chunks) can exhaust the heap even when the entry count is low. This byte budget is a second, independent bound on the same log: once the retained bodies exceed it, the oldest entries are evicted (oldest-first) until they fit. Whichever bound — count or bytes — is reached first evicts.

On by default, with a log-level-aware divisor. The default is derived from the JVM heap ceiling and is constant for the JVM's life. At INFO /WARN /ERROR /OFF the budget is a twentieth of the ceiling budget (the heap ceiling less 20 MiB); at DEBUG /TRACE it is a twelfth. On a 1 GiB heap (-Xmx1g) that is about 50 MiB counted at INFO and WARN and 84 MiB at DEBUG; on a 2 GiB heap, about 101 MiB and 169 MiB.

Why the INFO and WARN default is small, and what it costs you. The heap could safely hold about three times more (a seventh of the ceiling), but under heavy load entries kept that long outlive the garbage collector's short-lived memory area, get copied to long-lived memory, and keep the collector busy; on a 2-core, 1 GiB container (about 460 MiB heap) a seventh capped healthy throughput (the highest load with a median response time under 1 ms) at about 31,000 requests per second, while budgets either side of a twentieth kept it at about 36,000–38,000 by the same measure (the twentieth itself is interpolated from those runs). The trade-off is history: by default the log keeps about a third as many past requests as it would at a seventh wherever this budget is what limits the log (on large heaps with small bodies the entry-count limit maxLogEntries may bind first, so fewer are lost — at a 4 GB heap with small requests, about two-thirds are kept), so verify(), retrieve and the dashboard see fewer of them, and an upper-bound verification fails sooner once the oldest are evicted. At INFO the default was a twelfth until this release; a twentieth keeps about 40% fewer past requests than that, in exchange for less of the same garbage-collector work and a lower worst-case response time when the server is close to the most traffic it can log (measured on 2-core containers with 1 GiB and 2 GiB). If you need more history and are not running near your throughput limit, set maxEventLogSizeInBytes higher, for example to a twelfth or a seventh of your heap.

Entries still waiting to be logged have their own cap. When the server receives more traffic than it can log, a backlog of entries waits to be recorded. That backlog is capped at the larger of maxEventLogSizeInBytes and a seventh of the ceiling (a twelfth at DEBUG /TRACE), so a small budget does not cause log events to be dropped during a burst. Setting maxEventLogSizeInBytes above that cap raises the backlog cap with it; setting it to 0 removes both. The defaults are chosen so that the real heap the whole log holds, kept entries and backlog together, stays at or below about a quarter of the ceiling at either log level even under overload, leaving room for expectations, network buffers and the rest of the server.

Why the two levels differ. The budget counts an estimate of each entry's size, and the heap actually holds a multiple of that estimate which depends on your traffic. Measured on live heaps in September 2026 under both the G1 and ZGC garbage collectors, the log's kept entries held 0.50–0.97× their counted size at WARN and 1.04–2.31× at INFO, and the entries waiting to be logged held up to another 0.72× of theirs. The highest figures came from a server sent more traffic than it could log. The difference is that at INFO /DEBUG /TRACE MockServer writes every entry to system-out and keeps the formatted message (which embeds the body as text) on the entry for its whole life; once the log has caught up, forwarded proxy traffic is the most expensive case, because its message includes the request, the response and a curl command. Entries still waiting are not rendered yet, so this does not make the backlog itself heavier. An entry that quotes a request or response no longer keeps its formatted message, and re-measured in October 2026 the kept entries held 0.70–1.00× their counted size at INFO on JSON and proxy traffic, so the backlog cap at INFO is now the same seventh of the ceiling as at WARN, and the whole log still stays under about a fifth of the heap on that traffic. DEBUG and TRACE were not re-measured and keep a twelfth. The kept-history budget at INFO is now the same twentieth as at WARN; it used to be a twelfth.

This default is new in this release. Previously maxEventLogSizeInBytes was off unless you set it, so the log was bounded by entry count alone — which cannot protect a memory-constrained server, because a count cap treats a 10 MB body the same as a 10-byte one. If you are upgrading, you are gaining a bound that did not exist before; with large bodies the log may now keep fewer entries than it used to, and it evicts the oldest rather than running out of memory. The divisors were set from live-heap and throughput measurement: the backlog cap (a seventh of the ceiling, a twelfth at DEBUG /TRACE) keeps the worst measured whole log, kept entries plus the waiting backlog, at or below about a quarter of the heap ceiling, and the smaller twentieth at INFO and WARN keeps kept entries from slowing the garbage collector under load. Changing the log level changes both bounds together. If you share the heap with other large workloads and want a tighter bound, set maxEventLogSizeInBytes explicitly — note that a value below the default limits only the kept entries, not the backlog waiting to be logged; to limit that too, lower ringBufferSize or the heap (-Xmx); raise it if you want more retained history and have the heap headroom, or set it to 0 to bound the log by entry count only.

The budget counts each entry's body bytes, header bytes and a fixed per-entry structural overhead (via LogEntry.estimatedHeapSize()). It deliberately does not count the rendered log message — that is why DEBUG and TRACE keep a tighter backlog cap; an entry that quotes a request or response no longer keeps its message, which is why INFO now has the same backlog cap as WARN. The message is materialised after an entry's weight is fixed, and counting it would break the invariant that an entry weighs the same when evicted as when added.

Eviction is not silent. The first time the log evicts, MockServer logs a single WARN naming which bound was hit (count or bytes), its current value, and how to keep more coverage (for the entry-count limit, that includes lowering the log level or setting maxLoggedMatchFailures to keep INFO); and with the default failVerificationOnEvictedLog=true an upper-bound verification (never(), atMost(n), exactly(n), once(), between(a,b)) fails rather than silently passing on discarded evidence. Only these size-based bounds evict; the received-request and response entries a verification reads are recorded regardless of log level.

See Proxying LLM / Large-Body Traffic Without OOM for the recommended combo with disk capture.

An HTTP/1.1 client can send several requests on one connection without waiting for each response (pipelining). The responses must come back in the order the requests were sent, because the client pairs each response with a request by its position.

When true, MockServer handles one request on a connection at a time: a pipelined request waits until the response to the request ahead of it has been written. Responses therefore always come back in order, but pipelined requests on one connection are no longer handled at the same time, so the total time is the sum of their delays rather than the longest one. A request waiting behind a paused breakpoint or a streamed response is not recorded until its turn. Clients that do not pipeline (browsers, curl and most HTTP libraries by default) see no difference. A connection holding requests behind a response that makes no progress at all is closed after the idle connection timeout, so a lost response cannot hold them open forever.

When false, each pipelined request is handled as soon as it arrives, as in earlier versions, and a fast response can be written before a slower one sent ahead of it, which the client then pairs with the wrong request.

Maximum size in bytes of the headers of a request, all headers counted together, over HTTP/1.1, HTTP/2 and HTTP/3; also the most MockServer reads of an upstream server's response headers when it forwards or proxies

A request with larger headers is refused and is not matched against any expectation. The default, 256 KB, is well above what web servers and load balancers usually accept (8 KB to 64 KB) and fits large cookies and authentication tokens. Raise it if you deliberately send larger headers; set 2147483647 to remove the limit, which lets a client that keeps sending headers make MockServer hold them in memory. Zero or a negative value is read as 1.

How an over-limit request is refused depends on the protocol:

  • HTTP/1.1: 431 Request Header Fields Too Large, and the connection is closed.
  • HTTP/2: 431 on that request's stream, which is then reset; other requests on the connection carry on. If the headers as sent (compressed) are more than a quarter over the limit, the connection is closed instead.
  • HTTP/3: the connection is closed with the error H3_EXCESSIVE_LOAD; no 431 is sent.

Over HTTP/2 and HTTP/3 the size is counted the way those protocols define it: the name and value of every header plus 32 bytes each, including the method, host and URL (which are headers in those protocols), after decompression. A request with a long URL or a great many small headers therefore reaches the limit sooner over HTTP/2 or HTTP/3 than over HTTP/1.1. MockServer tells HTTP/2 and HTTP/3 clients the limit when they connect, and some clients will not send a larger request at all.

The same limit applies to the responses MockServer reads when it forwards or proxies a request: the headers of the upstream server's response, and its trailers, can be up to this size, over HTTP/1.1 and HTTP/2, so large Set-Cookie, Content-Security-Policy or token headers pass through. A response with larger headers is not passed on: the client is answered 502 with the reason as the body (for example upstream response headers are larger than maxHeaderSize (262144 bytes)), and it is logged once at WARN. When requests are sent through an upstream proxy (forwardHttpsProxy), the proxy's reply to CONNECT is limited the same way. So is an upstream server's reply to a WebSocket handshake that MockServer proxies: with larger headers the WebSocket is not opened and the client is answered 502. Before this, MockServer read at most 8 KB of an upstream's response headers whatever this was set to; if you have set it lower than 8192, upstream response headers are now limited to that lower value too. Mocked responses are not limited.

A request MockServer accepts can still be larger than the server it is forwarded to allows. MockServer sends it and passes on that server's answer, usually 431. Before, when forwarding over HTTP/2 on a connection where the server had already announced a smaller limit, MockServer did not send the request and answered 502.

Before this setting applied to HTTP/2 and HTTP/3, their headers were limited to 8 KB whatever it was set to. To restore that, set maxHeaderSize to 8192, which limits HTTP/1.1 headers to 8 KB too.

The trailers of an HTTP/2 or HTTP/3 request are limited like its headers, and a request with larger trailers is not matched either. Over HTTP/2 that request's stream is reset and other requests on the connection carry on; through a CONNECT or SOCKS tunnel a 431 is sent first if no response has started. Over HTTP/3 the connection is closed with H3_EXCESSIVE_LOAD.

This also limits the trailers that can follow a chunked HTTP/1.1 request body. Whatever value is set, MockServer rejects trailers once more than 8 KiB of them is waiting to be read, with a 400 response, and closes the connection.

The check applies to every way MockServer forwards or proxies a request: every forward action (httpForward, forward templates, forwards with a fallback, validating forwards, overridden forwarded requests, and class and object forward callbacks), requests that match no expectation and are proxied on (to the destination the client named, to proxyRemoteHost, or to a proxyPassMappings target), binary forwarding and WebSocket proxying. If false requests are assumed as binary if the method isn't one of "GET", "POST", "PUT", "HEAD", "OPTIONS", "PATCH", "DELETE", "TRACE" or "CONNECT"

MockServer decides from the first bytes of each connection. Bytes that cannot be the start of HTTP, TLS, SOCKS or HTTP/2 are decided straight away, however few they are. Bytes that could still be the start of one of those (for example GET with nothing after it) are held for up to one second in case the rest follows. Either way, what is not recognised is treated as binary, or as HTTP if this property is true.

When MockServer is proxying a binary connection to a remote host, a message that matches a binary expectation is answered by MockServer and every other message is forwarded as it is (see matchBinaryExpectationsWhenProxying, which you can turn off to forward every message). Otherwise it is matched against binary expectations, and if none matches MockServer replies with the text unknown message format, only HTTP requests are supported for mocking or HTTP & binary requests for proxying, but request is not being proxied and request is not valid HTTP and closes the connection.

Once a connection is binary, everything sent on it afterwards is treated as binary, with one exception: a TLS handshake. A protocol that starts in the clear and switches to TLS on the same connection is supported when mocking with binary expectations. For example, to mock a PostgreSQL server that accepts TLS: add a binary expectation that answers the 8-byte SSLRequest (00 00 00 08 04 d2 16 2f) with the single byte S, and binary expectations for the messages that follow. When the client then starts its TLS handshake, MockServer answers it with its own certificate, exactly as for a connection that starts with TLS (the same certificates, TLS protocols and client-certificate settings apply), and matches what it decrypts against the binary expectations, replying over TLS. Answer the SSLRequest with N instead and the connection carries on in the clear.

Unless binaryMessageFraming names the protocol (PostgreSQL, MySQL, Redis, or a length prefix you describe), MockServer does not know where a binary protocol's messages begin and end. It treats everything it can read from a binary connection in one go, up to 256 KiB, as one message, however many network reads or TLS records that takes. So a message is matched whole when all of it has arrived by the time MockServer reads it: a session of many small messages followed by a larger one (a query or a result of some kilobytes, for example) is matched message by message, in the clear and over TLS, and so is a connection's first message. Over TLS a message of one TLS record (up to about 16 KiB) is always matched whole, however the network delivers the record. What MockServer matches is still not always what the client meant as one message:

  • A message that reaches MockServer over time is matched as two or more messages, none of which has an expectation. That happens to a message larger than 256 KiB; to a message of more than one TLS record (about 16 KiB or more) when the records do not arrive together; and, in the clear, to a message that the client writes in several steps or that the network delivers in several packets with a gap between them. With the client on the same host, messages of up to 16,000 bytes over TLS and 40,000 bytes in the clear were always matched whole in measurements, and larger ones often were not; across a network, a message in the clear larger than one packet (about 1,400 bytes) can arrive in pieces.
  • Messages that the client sends one after another without waiting for a reply are matched as one message when they arrive together, which they do when the client writes them in one go. Give one expectation the bytes of all of them, and reply with the bytes of all their replies. This applies to TLS as well: two messages sent as two TLS records are one message when MockServer reads them together.

To mock a message that has no reply, give it a binary expectation whose response has no data: binaryResponse() or binaryResponse(new byte[0]) in Java, or "binaryResponse": {} in JSON (an empty binaryData means the same, and is returned without binaryData when the expectation is retrieved). MockServer then writes nothing and keeps the connection open. A message with no expectation at all gets the "unknown message format" text and the connection is closed, which is harmless for a message such as PostgreSQL's Terminate that ends the session anyway. If the client sends a message that has no reply together with the next message, the two arrive as one message, as described above.

A binary response can have a delay, as an HTTP response can: MockServer then writes the reply that long after the message arrived. Replies on one connection keep the order of the messages they answer, so a reply waits for any earlier reply on the same connection that is still delayed, even if its own delay is shorter or it has none. A message that matches no expectation is answered, and its connection closed, only after the delayed replies before it have been written. A response with no data has nothing to delay.

A client that sends messages but does not read the replies is not read either: once the replies MockServer has not yet been able to write to it pass 32 KiB, MockServer stops reading that client until it has read them, as it does when forwarding. The replies MockServer holds for one client are therefore limited, however much the client sends. Nothing is dropped; a client that writes much more than it reads sees its writes stall, as it would against any server.

The handshake is recognised by its first six bytes. A binary message sent in the clear that begins exactly like a TLS ClientHello is therefore taken for one, and a message of one to five bytes that could be the start of one (most plausibly the single byte 0x16) is held for up to one second before it is delivered. When MockServer is proxying binary messages rather than mocking them, it still answers the handshake itself and forwards each decrypted message on a new TLS connection to the remote host, so a remote server that expects the upgrade request on every connection will not accept them.

How MockServer cuts a binary (non-HTTP) connection into messages before it matches each one against your binary expectations, forwards it or logs it. With RAW, the default, MockServer does not know the protocol and treats what it reads in one go as one message (see Assume All Requests Are HTTP), so a message that arrives over time can be split and messages sent together are joined.

Name the protocol instead and MockServer reads where each message ends from the message itself:

  • POSTGRESQL: the length that each PostgreSQL message carries (the start-up message, SSLRequest, GSSENCRequest and CancelRequest have no type byte; every message after the start-up message has one).
  • MYSQL: the 3-byte length at the start of each MySQL packet. A packet is one message, except that a payload of 16 MiB or more, which MySQL sends as several full packets and a shorter last one, is one message made of all of them (headers included), as it is one command. A MySQL server speaks first, with its greeting, so to proxy MySQL also set forwardBinaryServerFirstWaitMillis (for example to 250) on a connection that has a forward target (port forwarding, transparent proxy or PROXY protocol): MockServer then opens the upstream connection and relays the server's greeting, and frames the client's packets, so with matchBinaryExpectationsWhenProxying (on by default) each packet can be answered by an expectation or forwarded. Mocking MySQL with no upstream server is not possible, as MockServer cannot send the greeting.
  • REDIS: one complete RESP2 or RESP3 value, with everything nested in it (a command is an array of bulk strings), or one inline command line such as PING. Values may nest at most 64 deep.
  • LENGTH_PREFIX: a length field you describe with binaryMessageLengthPrefixBytes, binaryMessageLengthPrefixByteOrder, binaryMessageLengthPrefixOffset and binaryMessageLengthIncludesPrefix, for a protocol that starts each message with its length (Thrift's framed transport, MongoDB's wire protocol, DNS over TCP, and many in-house protocols).

With any of them:

  • a message is matched as one message however it reaches MockServer: written in several steps, delivered in several packets, spread over several TLS records, or larger than 256 KiB;
  • messages sent together, such as an extended-query batch of Parse, Bind, Execute and Sync, or pipelined Redis commands, are matched one by one, so each needs an expectation of its own (one whose binary response has no data for a message with no reply), and their replies are written in the order of the messages;
  • it works in the clear and over TLS from the first byte. A TLS handshake part way through is recognised only where a new message would start: for PostgreSQL after an SSLRequest, for MySQL only straight after an SSLRequest packet (a MySQL packet can start with the same bytes as a handshake), and for Redis and length-prefixed messages at any message boundary. Bytes in the middle of a message are never taken for the start of a handshake;
  • it applies to proxied connections too, so with matchBinaryExpectationsWhenProxying (on by default) each message is matched or forwarded on its own. What the server sends back is relayed as it arrives; with POSTGRESQL, MockServer follows its messages only to know where each reply ends, for a binary response's upstream (see matchBinaryExpectationsWhenProxying). If the server sends a message whose length PostgreSQL does not allow, MockServer logs a warning and relays everything from then on unchanged.

A message may be at most maxRequestBodySize bytes (10 MiB by default), so a client cannot make MockServer hold more than that for one connection. A connection that declares a longer message, or sends bytes the protocol does not allow (a PostgreSQL length below the minimum, MySQL continuation packets out of sequence, a Redis value without its type byte or CRLF, or nested too deeply, a length prefix shorter than the bytes it must count), is closed at once and a warning is logged. MockServer holds a message until all of it has arrived; the bytes of a message that is not complete when the connection closes are discarded.

The setting applies to every binary connection on every port, so use it on a MockServer that mocks or proxies one protocol only. It is read when a connection is found to be binary, so changing it affects new connections only.

This is how MockServer proxies a binary (non-HTTP) connection; it is not a setting. Each client connection is given one connection to the upstream server, kept for as long as the client's connection lasts, and bytes are passed on in both directions as they arrive. This is what a protocol needs when the server expects a whole session on one connection, for example a database protocol where a client logs in and then sends queries, or when the server sends data the client did not ask for.

Changed in 9.0.0. Until 8.0.0 each message was forwarded on an upstream connection of its own. The settings forwardBinaryRequestsUseSingleConnection and forwardBinaryRequestsWithoutWaitingForResponse were removed in 9.0.0, together with that way of forwarding. A value still set for either, as a system property, environment variable or property-file key, is ignored, and MockServer logs one warning for it at start-up saying it was removed; in a JSON configuration it is ignored without a warning. Remove them from your configuration. A protocol in which every message stands alone works the same on one upstream connection.

What is different from 8.0.0:

  • The upstream server sees one connection for each client connection, not one for each message, and that connection stays open for as long as the client's does, even while nothing is sent.
  • There is no time limit on the upstream server answering: a client whose upstream never answers stays connected until one side closes. In 8.0.0 the client's connection was closed when no response arrived within maxFutureTimeout. TCP keep-alive (forwardSocketKeepAlive) still detects an upstream server that has gone away.
  • The event log has one "returning binary response" entry for each read from the upstream server, including reads that answer no message. In 8.0.0 it had one for each message.
  • Everything the upstream server sends is passed to the client, whether or not it answers a message. In 8.0.0 only the first bytes received on each per-message connection were passed on.
  • When the upstream server closes its connection, MockServer closes the client's connection, after passing on what the upstream sent, and does not treat that as an error. In 8.0.0 an upstream that closed after answering left the client's connection open, and the client's next message opened a new upstream connection.
  • When the client closes its connection, MockServer delivers what the client had already sent and then closes the upstream connection. An upstream server that has stopped reading has its connection closed 5 seconds after the client's close, whether or not it has taken everything.
  • A binaryProxyListener is called once for each message read from the client, as soon as it is read, in order, on a thread of its own. In 8.0.0 (without forwardBinaryRequestsWithoutWaitingForResponse) it was called once the response had arrived. The response it is given completes with the first bytes the upstream sends after that message, or with null if the client's next message arrives first or the connection closes. Bytes from the upstream that are not the response to a message (sent unprompted, or after the first bytes of a response) are passed to the listener's onUpstreamMessage method, if it overrides it; a listener that does not is not called for them.
  • A client or upstream server that is slower than the other is not buffered in memory: MockServer stops reading from the faster side until the slower side catches up, so a client that sends messages but does not read the replies is not read either. It does the same when more than 64 messages are waiting to be reported to the listener (for onUpstreamMessage it stops reading the upstream server, except while a message is waiting for its response). Nothing is dropped. If the upstream server takes none of the bytes waiting for it for responseWriteStallTimeoutMillis, both connections are closed.
  • If forwardProxyBlockPrivateNetworks is on, an upstream address it blocks is refused: the client's connection is closed and a warning is logged. Until 8.0.0 binary forwarding did not make this check.
  • If the upstream server cannot be reached, the client's connection is closed and a warning is logged, as before.
  • A client that turns TLS on part way through a connection, as a PostgreSQL client does with sslmode=require, can be proxied. What it sends before (PostgreSQL's SSLRequest) goes to the upstream server in the clear and the server's answer comes back; when the client starts TLS, MockServer answers it with its own certificate and starts TLS with the upstream server on the same connection, checking the server's certificate as for any forwarded TLS (forwardProxyTLSX509CertificatesTrustManagerType, forwardProxyTLSCustomTrustX509Certificates, forwardProxyTLSHostnameVerificationEnabled; the default trust type, ANY, accepts any certificate, so set it to JVM or CUSTOM to verify the server's certificate) and presenting forwardProxyPrivateKey / forwardProxyCertificateChain if the server asks for a client certificate. If that handshake fails or takes longer than socketConnectionTimeoutInMillis, both connections are closed and a warning is logged. In 8.0.0 each message the client sent over TLS went on a new upstream connection that started with TLS, which such a server does not accept.
  • A client that starts with TLS, from its very first byte, also gets one upstream connection for its whole connection, and that connection starts with TLS too: MockServer answers the client's handshake with its own certificate and makes its own handshake with the upstream server before sending anything, with the same certificate checks, client certificate and time limit as above. If that handshake fails, both connections are closed and a warning is logged. Until 8.0.0 each message went on a new TLS connection of its own, so a server that keeps a session (a database, a message broker) could not be proxied over TLS.
  • Through an upstream proxy. If the upstream server is reached through an upstream proxy, the one upstream connection is a tunnel through it, for clear connections and TLS alike, so a session protocol can be proxied through it: SOCKS5 for forwardSocksProxy, and HTTP CONNECT for forwardHttpsProxy or forwardHttpProxy (when both HTTP proxies are set, forwardHttpsProxy is used). If forwardProxyAuthenticationUsername and forwardProxyAuthenticationPassword are set, they are sent with the CONNECT. A server listed in noProxyHosts is connected to directly, and one forwardProxyBlockPrivateNetworks blocks is refused before anything is sent to the proxy. If the proxy refuses the tunnel (for example with 407 Proxy Authentication Required) or cannot be reached, the client's connection is closed and a warning is logged that names the proxy, the setting it came from and the status it answered with. In 8.0.0 a connection whose only upstream proxy was forwardHttpProxy had its bytes sent to the proxy as if it were the server, and a TLS connection, or a clear one with only forwardHttpsProxy set, went to the server directly, around the proxy; an HTTP proxy that does not allow CONNECT to the server's port now refuses the connection instead.
  • The name MockServer gives the upstream server over TLS (sent as SNI, and checked against the server's certificate when forwardProxyTLSHostnameVerificationEnabled is on) is the upstream's host name. When the upstream is known only by its IP address (a PROXY protocol header, transparent proxying, or proxyRemoteHost set to an address), it is the name the client sent MockServer, if the client sent one; otherwise no name is sent.

PostgreSQL through MockServer. Clients using sslmode=require work. Because the client sees MockServer's certificate, not the server's, two things behave differently from connecting directly:

  • SCRAM channel binding (SCRAM-SHA-256-PLUS, used by default by recent clients when the server offers it over TLS) fails, because it checks the certificate the client sees. Either turn it off in the client (channelBinding=disable for the JDBC driver, channel_binding=disable for libpq and psql), or, if you have the server's certificate and private key, give them to MockServer so it presents the same certificate: set privateKeyPath and x509CertificatePath to them, and certificateAuthorityCertificate to the certificate authority that signed the server's certificate.
  • Client certificates cannot be passed through: a server using cert authentication sees MockServer's client certificate.

PostgreSQL 17's direct TLS (sslnegotiation=direct) is not supported.

What is not supported:

  • Protocols in which the server speaks first (for example MySQL or SMTP), unless forwardBinaryServerFirstWaitMillis is set. MockServer only knows a connection is binary once the client has sent something, so by default it has not connected upstream before then.
  • Binary connections inside a CONNECT or SOCKS tunnel through MockServer. Binary proxying applies where the upstream is fixed: port forwarding (proxyRemotePort), a PROXY protocol header, or transparent proxying.

If true (the default), MockServer answers some messages of a proxied binary connection itself and forwards the rest. Each message the client sends is matched against your binary expectations. A message whose bytes equal an expectation's is answered with that expectation's binary response and is not sent to the upstream server; every other message is forwarded as usual. With no binary expectations, every message is forwarded. Set it to false to forward every message without consulting binary expectations.

Changed in 9.0.0: in 8.0.0 binary expectations were never matched on a proxied connection. If you proxy binary connections and keep binary expectations registered that you do not want to answer proxied messages, set matchBinaryExpectationsWhenProxying to false.

This lets a test use a real server for most of a session and fake one part of it. For example, with a PostgreSQL client in simple query mode and autocommit, you can return a canned result for one SELECT, or an error for one INSERT (with Times.once(), so the client's retry reaches the real server), or give a query no reply at all to test the client's time-out (an expectation whose binary response has no data).

It applies to every proxied binary connection, which is relayed on one upstream connection, directly or through a tunnel of an upstream proxy, forwardHttpProxy included (see Binary Proxying).

What happens upstream to a matched message is chosen per expectation, with the binary response's upstream:

  • ANSWER_ONLY (the default): MockServer writes the binary response and does not forward the message.
  • ANSWER_AND_FORWARD: MockServer writes the binary response and also forwards the message, so the server still sees it (an INSERT is really made, a PREPARE really exists); the server's reply to that message is dropped.
  • FORWARD_AND_REPLACE: MockServer forwards the message and, once the server's reply to it has ended, writes the binary response in its place. The client waits for the real server, so a reply to replace can fake a result while the server keeps its real state. With a delay, the replacement is written no sooner than that long after the message arrived, and the server's later replies wait behind it, so the client gets them in order.

The last two need binaryMessageFraming set to POSTGRESQL, because MockServer must know where the server's reply to one message ends. A reply ends where PostgreSQL says the server waits for the client again: at ReadyForQuery for a simple Query; for an extended-query batch (Parse, Bind, Describe, Execute up to Sync) the whole batch has one reply, ending at the ReadyForQuery after the Sync, so an expectation on the batch's Parse drops or replaces the reply to the whole batch (give the replacement every message the client expects, ParseComplete through ReadyForQuery; a client that sends Flush and waits for an answer before it sends Sync would wait forever for a replacement, so use ANSWER_AND_FORWARD for it); CopyData, Terminate and other messages without a reply have nothing to drop, and a replacement for one is written once the replies before it have ended. Without that framing an expectation that asks for either is answered as ANSWER_ONLY and MockServer logs one warning for the connection. A message matched without an upstream (plain mocking) is always answered as ANSWER_ONLY.

For example, in Java:

mockServerClient
    .when(binaryRequest(queryBytes))
    .respondWithBinary(binaryResponse(cannedRowsBytes).withUpstream(BinaryResponse.Upstream.FORWARD_AND_REPLACE));

or as JSON: "binaryResponse": { "binaryData": "...", "upstream": "FORWARD_AND_REPLACE" }.

Things to know before you rely on it:

  • The upstream server never sees a message answered with ANSWER_ONLY. Your canned reply must be true for the state the server is really in. For PostgreSQL that means: reply with the transaction status the session really has (ReadyForQuery with I outside a transaction); do not answer statements whose effect later statements depend on (BEGIN, SET, PREPARE, a Parse for a named statement); do not answer the start-up, authentication or SSLRequest messages.
  • A message must arrive exactly as the expectation's bytes. Unless binaryMessageFraming names the protocol, MockServer does not know where a binary protocol's messages begin and end: what it reads in one go is one message (see Assume All Requests Are HTTP). Two messages sent together are one message, and a large message can arrive as several. When the bytes differ in any way there is no match and the bytes are forwarded unchanged, so the session is not broken, but the real server answers. Check in your test that the expectation was matched, not only that the client got an answer. The easiest way to get the exact bytes is to run the client once through MockServer and copy the message from its log.
  • Order between MockServer's replies and the server's. Replies from the server reach the client in the order the server sent them, and MockServer's replies in the order of the messages they answer, but nothing orders the two against each other. A client that waits for each reply before sending its next message is not affected. If MockServer writes a reply while a forwarded message has had no response yet, it logs a warning saying the two may reach the client out of order.
  • An expectation whose action is not a binary response (for example an HTTP response) does not answer a proxied message: the message is forwarded and a warning is logged.
  • An expectation with an empty binary request, or with not, matches every message (or every other message), so nothing (or almost nothing) is forwarded.
  • An answered message is logged as it is when mocking without an upstream, and is not reported to a binaryProxyListener, which sees only what was sent to the upstream server. A connection whose messages are all answered opens no upstream connection.
  • Cost. A message on a relayed connection is matched against the expectations only when one could match it: when a binary expectation has exactly its bytes, or while a binary expectation without bytes or with not, or a conditional expectation, exists. Every other message is forwarded without being matched, and adds no match or no-match entries to the log; the log still shows each message MockServer received and forwarded. With no binary expectation registered, no message is matched.
  • A binary response's delay holds back MockServer's reply as it does without an upstream (see Assume All Requests Are HTTP). Replies from the server are not held behind it, so one can reach the client first; only a FORWARD_AND_REPLACE replacement, which takes the place of a server reply, holds back the server's replies after it.
  • A message forwarded with ANSWER_AND_FORWARD or FORWARD_AND_REPLACE is reported to a binaryProxyListener like any forwarded message, with what the server sent. A server message that arrives while a reply is being dropped, such as a notice, is dropped with it.

By default (true) MockServer pools idle keep-alive HTTP/1.1 upstream connections (keyed by host, port and scheme) and reuses them for subsequent requests to the same upstream. Reusing the upstream's keep-alive connections eliminates repeated TCP and TLS handshakes, significantly improves throughput for proxy-heavy workloads that repeatedly call the same upstream, and avoids ephemeral-port exhaustion under sustained forward load (where opening a fresh connection per request can exhaust the operating system's available local ports and cause request failures). Set this to false to open a fresh upstream connection per request that is closed once the response is received (the historical behaviour) — useful only for unusual upstreams.

Pooling is safe to leave on: a connection is only returned to the pool when it is genuinely clean — its HTTP client codec must have no leftover undecoded bytes after the response, and any uncertainty closes the connection instead of pooling it. MockServer's error() action (which deliberately returns raw, non-HTTP bytes and/or drops the connection) — or any malformed upstream reply — is therefore never pooled, so a later request can never reuse a corrupted connection.

HTTP/1.1 keep-alive connections and HTTP/2 connections are pooled (an HTTP/2 connection is reused with a fresh stream per request), so a proxy whose client negotiated HTTP/2 in an HTTPS CONNECT tunnel no longer opens a new upstream connection for every request. HTTP/3, binary forwarding, streaming (Server-Sent Events) responses, and proxy-tunnelled connections are never pooled. A connection the upstream closed, that returned Connection: close, or that returned a reply which did not parse as valid HTTP is never reused and falls back to a fresh connection.

How many times MockServer forwards the same request before it stops a forwarding loop. A forward, a proxyPassMappings entry, or a forwarded WebSocket upgrade whose host and port lead back to MockServer itself would otherwise match the same expectation or mapping again on every hop, opening a new connection each time until MockServer runs out of local ports or open files.

Data Plane Authentication Configuration:

These properties optionally require authentication on the mocked endpoints (the data plane), separate from the control plane (/mockserver/*) and the HTTP CONNECT proxy. The feature is opt-in and off by default — when disabled (the default) MockServer behaves exactly as before and mocked endpoints are open.

When enabled, configure one or more schemes (HTTP Basic, Bearer token and/or API key). A request is accepted if it satisfies any one of the configured schemes. Requests with missing or wrong credentials receive 401 Unauthorized before the request reaches expectation matching. The control plane and the health/status/ready probes are not affected, so you can still administer a server whose data plane is locked down. Only requests MockServer actually handles as control-plane requests are exempt: any other path, including a /mockserver/... path MockServer does not handle (or a path such as /mockserverfoo), is treated as a mocked endpoint and needs credentials. gRPC requests without credentials, bidirectional streams and gRPC server reflection included, get gRPC status UNAUTHENTICATED. The gRPC health check (grpc.health.v1.Health/Check) stays open, like the other health probes.

Where it applies: data-plane authentication applies to the standalone MockServer server (the JAR, the Docker image, the Helm chart, and the JUnit, Spring and Testcontainers integrations, all of which run it), to the WAR deployments (mockserver-war and mockserver-proxy-war) and to the in-process server (InProcessMockServer). It has no effect on DNS mocking, because DNS queries carry no HTTP credentials.

In-process server: a request passed to InProcessMockServer.handle must carry the credentials in its headers (Authorization or the API-key header), exactly as it would over HTTP. There is no TLS connection, so tlsMutualAuthenticationRequired does not apply and a client certificate set on the request is not accepted as a credential. The Java methods (upsert, verify, reset and so on) are calls from your own code and need no credentials.

WAR deployments: the servlet container, not MockServer, terminates TLS. With tlsMutualAuthenticationRequired=true a mocked request must arrive over HTTPS (otherwise 426 Upgrade Required) with a client certificate the container has verified (otherwise 401 Unauthorized). Configure the container to ask for client certificates and to verify them against your CA, for example Tomcat's certificateVerification="optional" (or "required") with a trust store, and never a setting that skips verification, such as "optional_no_ca", because MockServer accepts any certificate the container reports. tlsMutualAuthenticationCertificateChain has no effect in a WAR.

Fail-closed: if you set dataPlaneAuthenticationRequired=true but configure no scheme, every mocked request is rejected (rather than allowed) — this prevents a misconfiguration from silently leaving the data plane open.

Some optional LLM features need MockServer to call a real LLM you already run — for example drift detection (replaying recorded fixtures against the live provider), exploratory semantic prompt matching, and the plain-language summary that PUT /mockserver/explain?narrate=true adds when llmExplainNarrationEnabled is on. These features are off unless a backend is configured, and they fail closed: if a configured backend times out or errors, the feature behaves exactly as if it were unconfigured and logs a single line. A real LLM call is never placed on the deterministic assertion/matching path.

A backend can be supplied three ways (simplest first):

  1. Provider environment conventions — if OPENAI_API_KEY, ANTHROPIC_API_KEY, GEMINI_API_KEY, or OLLAMA_HOST is already set (the same variables each provider SDK reads), MockServer auto-detects a backend. No MockServer configuration needed.
  2. A single default backend via the properties below.
  3. Named backends via a JSON file (mockserver.llmBackendsConfig) for multiple or advanced setups.

llmProvider selects which backend llmApiKey / llmModel / llmBaseUrl talk to, and accepts one of the Provider enum names: ANTHROPIC, OPENAI, OPENAI_RESPONSES, GEMINI, AZURE_OPENAI, OLLAMA, or BEDROCK. Ollama is the easiest to start with — it needs no key and runs locally. llmModel overrides the provider's default model (for example gpt-4o, claude-sonnet-4-5, or an Ollama-pulled model name); leave it empty to use the provider's own default. llmBaseUrl overrides the provider's default API endpoint — set it to point at a self-hosted or proxied endpoint (for example a local Ollama server, or an OpenAI-compatible gateway); leave it empty to use the provider's standard endpoint. AZURE_OPENAI has no standard endpoint, so it needs llmBaseUrl set to your resource (for example https://my-resource.openai.azure.com); without it no request is sent. The API key is a secret and is redacted (***) anywhere configuration is logged.

Changing the endpoint at runtime clears the key. A PUT /mockserver/configuration request that changes llmBaseUrl, or changes llmProvider while llmBaseUrl is empty (so the provider's own endpoint is used), without also supplying llmApiKey, clears the key MockServer holds and logs a warning, so the key is never sent to the new endpoint. Supply the key again in the same request as the new endpoint to keep using the backend. The ***REDACTED*** value a GET returns does not count as supplying it.

llmBackendsConfig takes the path of a backends JSON file, and the path is shown as you set it — the keys live in the file, which MockServer never returns. If you set the JSON document itself as the value instead, every apiKey in it is masked with ***REDACTED*** when the configuration is read back, and the rest of the document is shown so you can still see which backends are configured. A value that contains JSON but cannot be read as exactly one document is masked in full rather than shown, so nothing hidden inside it can leak. Sending a masked document back is safe, but if you rename or re-order a backend whose key you only ever saw masked, MockServer can no longer tell which key belongs to it — it then applies none of the document and logs a warning, rather than saving a backend with its key silently removed. Supply that backend's real key alongside the rename. The same happens if you change a backend's baseUrl or provider while leaving its key masked, so a key is never sent to an endpoint it was not set for.

Writes the bytes MockServer receives and sends to its console log, like WireMock's --print-all-network-traffic. Use it when you need to see exactly what a client sent or what MockServer answered, for example a malformed header, a missing Content-Length or a line ending that is not \r\n.

This is a debugging aid only: do not use it in production. Request and response bodies, query strings and the hex dump of non-HTTP traffic (including its text column) are written as they were sent, up to 4,096 bytes per read or write, so the log can hold passwords, tokens and personal data. Only the header values listed below are masked. Turn it on while you debug, treat the output as sensitive, and turn it off afterwards.

What is logged:

  • Every connection to MockServer: HTTP/1.1 (including WebSocket traffic after the upgrade) as text after TLS has been decrypted, HTTP/2 as decoded frames (HEADERS, DATA, SETTINGS and so on, because HTTP/2 compresses headers on the wire), and connections MockServer does not recognise as HTTP as a hex dump.
  • The HTTP requests MockServer sends itself: forwarded and proxied requests and webhooks, labelled forward connection. When the setting is made for the whole JVM (system property, environment variable or properties file), the requests of a MockServerClient running in the same JVM are logged too, also labelled forward connection.
  • Traffic tunnelled through MockServer as an HTTPS (CONNECT) or SOCKS proxy is logged decrypted, on the connection MockServer opens to itself for the tunnel, not on the client's encrypted connection.

Not logged: HTTP/3, the connection MockServer opens upstream for a proxied WebSocket or a relayed binary connection (what it carries is logged on the client's connection), requests between cluster members, metrics export, DNS, and TLS and SOCKS handshakes.

How it is shown: at most 4,096 bytes of each read or write, then how many more bytes were left out. Each entry starts with one line naming the connection; every line after it starts with | , and line breaks, carriage returns and other control characters in the traffic are shown as \n, \r and \xHH, so what a client sends cannot pass for a log line of its own.

Reading the configuration back with GET /mockserver/configuration masks the value of any credential-bearing header (Authorization, Api-Key, X-Auth-Token and similar) with ***REDACTED***; every other header is returned exactly as you set it, so the example above reads back as Api-Key=***REDACTED***,X-Scope-OrgID=tenant-a. Sending that masked list straight back with PUT /mockserver/configuration is safe — the masked header keeps the real value MockServer already holds, while any header you edited is applied normally.

When you edit a masked header list, leave each ***REDACTED*** exactly as it was returned — you may rename, add, remove and re-order the other headers freely. To replace a credential, type the new value on its own in place of the whole ***REDACTED***; do not type it next to the mask.

If MockServer cannot work out which real value a ***REDACTED*** stands for, it applies none of the header list, logs a warning saying so, and keeps the headers it already holds. It will neither send the text ***REDACTED*** to your metrics endpoint as a credential nor quietly drop the header and leave you with no credential at all. If a header list you sent does not appear to have taken effect, check the log for that warning. That happens when:

  • the mask was edited into the middle of a value, or text was typed onto the end of it;
  • no value is held under that header name. Changing only the capitalisation of a name is fine — HTTP header names are case-insensitive, so MockServer still finds the value — unless the list contains two names that differ only in case, in which case they are two separate headers and MockServer cannot tell which value the mask belongs to;
  • the real value you have configured itself contains the text ***REDACTED***. That is indistinguishable from a mask, so edited lists are refused until you replace that header's value with a real one.

The credential MockServer presents when it queries other cluster nodes during verify/retrieve fan-in. If your MockServer control plane requires authentication (a bearer token, JWT, or OIDC), the fan-in queries to other nodes would otherwise be rejected and the whole verify/retrieve would fail. Set this to the credential each node should send — it is used exactly as given for the Authorization header, so include the scheme, for example Bearer eyJ.... Set the same value on every node. Default is empty (no credential sent — unchanged behaviour); leave it empty if your control plane is not authenticated. Because it is sent on every cross-node query, treat it as a shared secret and prefer TLS between nodes. Has no effect unless clusterVerifyFanIn is enabled. Like every other credential property it is write-only: GET /mockserver/configuration does not return it. It is also fixed at startup: a PUT /mockserver/configuration request cannot change it (a different value is ignored and a warning is logged that never shows the token).

Cloud Blob Store Configuration:

These properties configure cloud-backed blob storage for durable persistence of expectations, cassettes, and fixture files. Each cloud backend requires its own optional module on the classpath. Set blobStoreType to s3, gcs, or azure and configure the backend-specific properties below.

Selects where MockServer stores blob data such as persisted expectations, recorded cassettes, and fixture files. The default filesystem backend writes blobs to the local disk (preserving the existing on-disk persistence behaviour). How many seconds MockServer waits, while starting up, for previously persisted expectations to be read back from a cloud blob store before giving up and starting anyway.

This read happens before MockServer starts listening, so an unreachable or misconfigured blob-store endpoint would otherwise delay startup for the cloud SDK's own retry budget — around two minutes for AWS — long enough to fail a Kubernetes readiness probe or a test-container wait. When the wait expires MockServer logs a warning and starts with no restored expectations.

Set to 0 to skip the startup restore entirely. Only relevant when persistExpectations is enabled and blobStoreType is a cloud backend (s3, gcs or azure) — the filesystem backend reloads via initializationJsonPath instead.

This value is read once, while MockServer starts, so it must be set before startup. Like the other blobStore settings it is reported by GET /mockserver/configuration, but changing it with PUT /mockserver/configuration on a running instance has no effect — the restore it governs has already happened.

Type: int Default: 10
