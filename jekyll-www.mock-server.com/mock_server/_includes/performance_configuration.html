Memory Tuning Guide

MockServer stores expectations and log entries in memory using ring buffers. The two most important settings that affect memory usage are maxExpectations and maxLogEntries. Each HTTP request processed by MockServer generates 2-3 log entries (the request itself, the expectation match result, and the response). Because maxLogEntries caps the entry count and cannot see how large each entry is, a workload with large bodies is bounded instead by maxEventLogSizeInBytes — a byte budget that is on by default, and the defaults (this budget plus a separate cap on entries still waiting to be logged) keep the whole log at or below about a quarter of the heap ceiling, so a few large bodies cannot exhaust the heap through a count-only cap. At WARN and quieter the default keeps about a third as much as a seventh of the heap would, so that under heavy load kept entries do not slow the garbage collector; raise maxEventLogSizeInBytes if you need more request history for verify or the dashboard.

Both settings have automatic defaults derived from the JVM heap size (the -Xmx maximum, as the JVM reports it, whichever garbage collector you use), so the default is the same for every MockServer instance in a JVM regardless of how much memory is already in use. On larger heaps the default maxLogEntries scales up to 250,000 entries, so more request history is retained before the oldest entries are overwritten; the byte budget (maxEventLogSizeInBytes) still bounds total memory. The table below provides recommended values if you want to override the defaults for different heap sizes:

JVM Heap Size maxExpectations maxLogEntries Approx HTTP Requests Retained
256 MB 1,000 5,000 ~1,500 - 2,500
512 MB 2,000 15,000 ~5,000 - 7,500
1 GB 5,000 40,000 ~13,000 - 20,000

These are conservative estimates assuming typical request/response sizes of 1-5 KB. Large request or response bodies will consume more memory per entry.

Tips for reducing memory usage:

  • Reduce maxLogEntries to limit the number of stored request/response log entries
  • Reduce maxExpectations if expectations contain large response bodies
  • Increase JVM heap size (-Xmx) to give the garbage collector more headroom
  • Use outputMemoryUsageCsv to monitor actual heap usage and tune values accordingly

Docker example with memory-constrained settings:

docker run -d --rm -p 1080:1080 \
  --env MOCKSERVER_MAX_EXPECTATIONS=1000 \
  --env MOCKSERVER_MAX_LOG_ENTRIES=5000 \
  mockserver/mockserver

Troubleshooting: MockServer Becomes Slow or Unresponsive

If MockServer appears to freeze, hang, or become progressively slower under sustained load, the most likely cause is memory pressure from log entry accumulation. This section explains why it happens and how to fix it.

If instead connections are being refused or failing to open, this is not the section you want. Two errors in particular are operating-system limits rather than MockServer, and neither is fixed by any MockServer setting:

  • Too many open files, or Netty's ChannelException: Unable to create Channel — the process has run out of file descriptors, one of which every connection needs. On macOS the JVM caps this at 10,240 however high you set ulimit -n, and the fix differs between macOS and Linux.
  • Can't assign requested address / BindException — the client machine has run out of ephemeral source ports. This one is never the server.

See Concurrent connection limits are set by the OS and the JVM for the cause of each and what to change.

Why Does MockServer Slow Down?

MockServer keeps a record of every request it processes and every response it sends. This is a deliberate feature, not a side-effect of logging — it is what makes verify, retrieveRecordedRequests, and the dashboard work. Because these entries exist to support verification, they are stored regardless of the configured log level. Lowering the log level reduces the diagnostic output written to stdout and cuts per-matcher allocation on the matching hot path (see the note on log level below), but the request and response records themselves are always written to the in-memory store. Many users reach for the log level first when they notice slowness; that will not fix this cause.

The store is bounded: when it fills up, the oldest entries are evicted to make room for new ones. Under sustained load, entries are evicted and replaced continuously, and the JVM must reclaim the memory those evicted entries held. It does this by periodically stopping all application threads briefly — a garbage collection pause. Most requests land between pauses and see very low latency. But the small fraction of requests that arrive just as a collection starts must wait for it to finish. This is why a load test can show a comfortable median alongside an alarming p99: the median reflects the majority of requests that were never affected, while the tail captures the unlucky few that waited behind a pause.

Request rate, not response body size, is the primary driver. Even a response of just a few bytes creates a log entry dominated by request metadata, headers, and match context — each entry occupies roughly 4–10 KB of heap regardless of whether the body is 6 bytes or 6 kilobytes. At high request rates the ring buffer turns over quickly, triggering eviction and collection more and more often. Measured on a deliberately heap-constrained server to make collections visible: garbage collection consumed 6.6% of wall-clock time at around 48,000 requests per second, with pauses averaging around 56 ms each. The number of collections rose almost perfectly in step with request rate; each individual pause stayed roughly the same length. More load means more pauses, not longer ones — but as the rate climbs, more requests fall inside them and the tail grows. A workload returning a 6-byte response at 8,000 req/s showed a sub-millisecond median alongside a p99 in the tens of milliseconds. Response body size shifts the numbers but does not change the pattern. The constrained-heap figures here are from a test server sized to make collections frequent and visible; on a larger production heap the allocation volumes per minute are the same, but each collection comes less often against a bigger budget.

There is a further practical point. At around 40,000 req/s, the default store holds roughly one second of history — at 8,000 req/s the same store holds roughly five seconds. At high throughput, the store is costing latency tail to retain a window that most users could never query in time anyway. This is the sharpest argument for reducing maxLogEntries when running at high rates: the GC pressure drops, and the history window you give up is already far too short to be useful.

The table below shows log allocation throughput at a range of rates and body sizes. The high-rate figure is derived from the per-entry cost above at its lower bound (two entries of 4 KB per request) and is therefore a floor, not a ceiling — larger headers or a third entry per request push it higher. The high-rate row shows that at 8,000 req/s even a tiny response generates the better part of four gigabytes of allocation per minute — far more than any of the body-size comparisons.

Request Rate Response Body Size Log Data Generated Per Minute
1 req/s 1 KB ~1 MB
10 req/s 1 KB ~12 MB
10 req/s 100 KB ~120 MB
1 req/s 1 MB+ ~120 MB
8,000 req/s ~10 bytes (body barely matters; metadata dominates) ~3,750 MB or more

Large response bodies increase the per-entry cost and make the problem worse at any given rate — a single expectation returning a very large response at even a modest rate can generate a significant volume of log allocation. But body size is a multiplier on a pattern that is already present at high request rates with tiny responses.

Note: Expectations with large response bodies also consume heap proportionally (e.g., a 50 KB response body results in ~55-75 KB per stored expectation). If you have many expectations with large bodies, reduce maxExpectations as well.

How To Fix It

Apply one or more of the following, depending on your use case:

Fix When To Use Trade-off
Increase JVM heap size Gives the GC more headroom so it collects less often — useful at high request rates and with large response bodies Uses more container/host memory
Reduce maxLogEntries The single most effective fix at high request rates — fewer entries to evict means less collection work. At high rates (thousands of req/s) the default store already holds only seconds of history, so you are giving up very little by bounding it tightly Fewer requests available for verification
Reduce maxExpectations When expectations contain large response bodies Fewer expectations can be stored simultaneously
Switch to ZGC (-XX:+UseZGC) Heap ≥ 4 GB and matcher latency matters — typically gives single-digit-millisecond GC pauses where G1 commonly sits in the 50–200 ms range under sustained allocation Fixed memory overhead (less attractive below ~4 GB); set -Xms and -Xmx to the same value (e.g. -Xms4g -Xmx4g) so the heap is pre-committed

Note on GC selection: the MockServer Docker images already run generational ZGC by default (from v8.x) — you get the lower tail latency below without setting anything, and can revert with JAVA_TOOL_OPTIONS=-XX:+UseG1GC. The guidance here applies mainly to the standalone JAR, where the JDK default collector (G1) is used unless you pass -XX:+UseZGC yourself. ZGC has been production-ready since Java 17, and -XX:+UseZGC can cut p99 matcher latency for deployments with deep ring buffers (high maxLogEntries) or large heaps, by holding stop-the-world pauses to the single-digit-millisecond range. Which ZGC you get depends on the Java version. From Java 23 onwards ZGC defaults to generational and -XX:+UseZGC alone selects it — that is what the MockServer Docker images give you, since they bundle Java 25 or later (the -clustered image bundles Java 21). On Java 22 and earlier, including Java 21, the same flag gives the older non-generational collector unless you add -XX:+ZGenerational; on Java 17 only the non-generational collector exists. Java 24 removed the non-generational mode altogether. Generational ZGC reaches noticeably shorter pauses than the 1–5 ms typical of the non-generational one. The separate -XX:+ZGenerational flag was removed in Java 24 — passing it there does no harm, but it is ignored with a warning, so drop it. For a standalone-JAR sidecar with a very small heap the JDK default collector is fine — ZGC carries a fixed memory overhead. On the Docker images, though, ZGC is the default even on small containers: testing showed it lower request tail latency on the default container heap without OOM-killing a 512 MB or 1 GB container (under load it grows to its full heap and keeps it while the load lasts, in memory the kernel cannot reclaim, and it holds roughly 60–80 MB more idle memory than the previous default; the images’ 45%-of-limit heap cap leaves room for that down to the 512 MB floor, or 768 MB for a -clustered node with the Infinispan backend), so the earlier “only worth it above ~4 GB” guidance does not apply to the way the images are configured. In containerised deployments using ZGC, size the container memory limit at ~1.5× your -Xmx value to leave headroom for JVM overhead (code cache, metaspace, thread stacks) and Netty’s direct buffer pool. Note that ZGC multi-maps the same physical pages for its coloured-pointer scheme; under some cgroup RSS-accounting modes those pages are counted multiple times against the container limit, so the process can be OOM-killed even though the actual physical footprint fits (e.g. -Xmx4g → --memory=6g). Shenandoah is not recommended — it is not available in every JDK distribution, so ZGC is the simpler choice.

Note on logLevel and disableLogging: the received-request and response log entries — the ones a verify reads — are always stored regardless of log level, so lowering the level never breaks verification. But the per-expectation match / did-not-match diagnostic entries are stored only at INFO or more verbose: at WARN they are neither produced nor retained. So on a workload with many expectations, running at WARN genuinely reduces the number of entries retained per request (a request that scans N expectations before matching can log up to N diagnostic entries at INFO), which lowers memory and the pressure on the entry-count limit (maxLogEntries) without affecting what verify can find — the default byte budget is the same at WARN as at INFO, though smaller than at DEBUG /TRACE, so coming from those levels on a workload where that budget is what evicts, raise maxEventLogSizeInBytes too — the cheapest safe lever when a memory-constrained server is under load. It does not reduce the memory held by large request/response bodies, which are on the always-retained entries; for those, the byte budget (maxEventLogSizeInBytes, on by default) bounds the kept entries, and entries still waiting to be logged are capped at the larger of that budget and a seventh of the heap ceiling (a twelfth at DEBUG /TRACE) — the server drops waiting entries rather than OOM-ing when that cap is reached (see the heap-sizing section below). WARN drains the waiting entries faster (and, from DEBUG or TRACE, widens their cap by about 70%), so it remains the cheapest lever against drops for large-body workloads; the default kept history is the same at INFO and WARN (a twentieth of the heap ceiling, against a twelfth at DEBUG /TRACE), so raise maxEventLogSizeInBytes if you need more of it. maxLoggedBodyBytes (per-entry body truncation) reduces the deque's steady-state body footprint — truncation runs in the consumer, after the ring, so it does not reduce the ring's in-flight byte contribution — and breaks verification against body content — a verify that matches on body will fail against a truncated entry; verification by path, method, and header is unaffected. disableLogging and disableSystemOut only silence log output — they do not stop requests being recorded, so neither reduces heap or GC pressure. Reaching for either when you see latency or memory pressure will not help; use the levers above (log level, maxLogEntries, maxEventLogSizeInBytes, maxLoggedBodyBytes) instead.

Note on logLevel and matching throughput: beyond the retained-entry saving above, running below INFO also cuts transient per-request allocation on the matching hot path. At INFO, every request that scans expectations builds and logs a diagnostic “matched”/“did not match because…” message per matcher; below INFO that work — the per-matcher log entry and the human-readable “because” string assembly — is skipped entirely. For a deployment with many expectations under sustained load this is the single largest matching-path allocation, so running at WARN noticeably cuts allocation churn and GC pressure (it does not change which requests match, only whether the diagnostic narrative is produced). Lowering the level therefore helps on two fronts — fewer retained diagnostic entries (memory) and less transient allocation (throughput/GC) — while leaving the received-request/response entries that verify depends on fully intact.

Note on logLevel and high request rates: logging at INFO is produced by a single background thread, and on a busy server that thread can fall behind the rate requests arrive — in our own load tests we estimate this starting roughly from 8,000–10,000 requests/second on a 6-core server with four expectations, where the request matches the last one (about six log entries per request: the match attempt against each of the first three, the match, and the recorded request/response). Each expectation checked before a match adds another log entry, so with more expectations the same server starts dropping at a lower request rate — roughly half as many requests per second with ten (again matching the last one). Past that point, log entries are dropped, which can mean a request is missing from retrieveRecordedRequests, from the dashboard, or from a verify — by default (failVerificationOnEvictedLog), an upper-bound verify (never(), atMost(n), exactly(n), once(), between(a,b)) fails rather than passes once this happens, naming the drop in its failure message, until the log is reset or cleared entirely. A once-only WARN (“Log event ring buffer full — dropping log events…”) naming the remedies below is logged the first time this happens after each reset regardless of metricsEnabled, unless logging or system-out is disabled. For high-throughput tests that call verify, run at WARN or ERROR instead of the INFO default — it keeps the entries verify needs while skipping the per-expectation diagnostics that saturate the logging thread. To keep INFO, set maxLoggedMatchFailures (for example to 10) instead: it caps how many of those diagnostics each request writes, and leaves which expectation matches and the closest-match entry unchanged. You can also watch this happening with metricsEnabled set to true: the mock_server_dropped_log_events Prometheus counter (these drops carry the label reason="ring_full") and the dashboard's log-pressure banner both need it, and show nothing while it is off (the default).

Recommended Configurations

High-throughput workloads (any response size — this applies regardless of body size; request rate is the driver):

docker run -d --rm -p 1080:1080 \
  -e MOCKSERVER_MAX_LOG_ENTRIES=5000 \
  mockserver/mockserver

Large response bodies (e.g., responses >100 KB):

docker run -d --rm -p 1080:1080 \
  -e JAVA_TOOL_OPTIONS="-XX:+UseZGC -Xmx1g" \
  -e MOCKSERVER_MAX_LOG_ENTRIES=1000 \
  -e MOCKSERVER_MAX_EXPECTATIONS=100 \
  mockserver/mockserver

Maximum throughput, minimal memory (verification limited to most recent requests):

docker run -d --rm -p 1080:1080 \
  -e JAVA_TOOL_OPTIONS="-XX:+UseZGC -Xmx512m" \
  -e MOCKSERVER_MAX_LOG_ENTRIES=100 \
  -e MOCKSERVER_LOG_LEVEL=WARN \
  mockserver/mockserver

MOCKSERVER_LOG_LEVEL=WARN drops the per-matcher diagnostic logging on the matching hot path (see the note above), which is the largest matching-path allocation when many expectations are registered. If your matchers rely heavily on regular expressions and your patterns and inputs are trusted, also add -e MOCKSERVER_REGEX_MATCHING_TIMEOUT_MILLIS=0 to evaluate regexes inline and skip the per-regex thread hand-off (this removes the catastrophic-backtracking guard — see Regex Matching Timeout).

Configuring JVM Heap Size

The MockServer Docker image caps the JVM heap at 45% of the container's memory limit (-XX:MaxRAMPercentage=45.0), so the in-memory ring buffers size off a bounded heap. Always run the container with an explicit memory limit of at least 512 MiB (768 MiB for a -clustered node with the Infinispan backend) (for example --memory=2g, or resources.limits.memory in Kubernetes) — without one the JVM sizes its heap off the host's total memory, and the default ring sizes (maxLogEntries and maxExpectations, which derive from available heap) scale up with it, so MockServer can be OOM-killed under load.

Sizing the container for your workload. The heap is only part of what the Java process occupies, and — this is the part that trips people up — the rest is not a fixed fraction of the heap. It is largely additive and driven by load, not by heap size. Under sustained load a 1,536 MiB heap was measured occupying 2,271 MiB of real memory; the 735 MiB difference breaks down as:

  • class metadata (metaspace) and the JIT code cache — about 133 MiB, and roughly constant regardless of heap;
  • one stack per thread — tens of MiB, set by the thread count (which tracks CPU cores), not the heap;
  • the garbage collector's own bookkeeping — this part does scale with the heap;
  • and the largest, most variable piece: the pool of direct (off-heap) network buffers Netty uses for request and response bodies, whose size is driven by concurrency and body size rather than by the heap, and which is capped at a quarter of the heap (see Off-heap buffer limit below).

None of that is counted by -Xmx, and most of it does not shrink when you shrink the heap. So the practical model is footprint ≈ heap + overhead, where the overhead is dominated by heap-independent, load-driven terms. A 75% cap could not fit — at 75% of a 2 GiB limit the heap alone (1,536 MiB) plus this overhead exceeded the limit and the kernel killed the process. 60% did not fit at the small end either: the Z garbage collector (the images' default) under load grows to its full heap and keeps it while the load lasts, in memory the kernel cannot reclaim, so at 512 MiB a 308 MiB heap plus about 150 MiB of other JVM memory and about 20 MiB of kernel socket buffers for ~4,800 connections left almost nothing, and the container was killed under load. That is why the default is 45%: at 50% the container survived, but in some runs peaked above 90% of its limit.

The convenient “budget about 1.5× the heap” shorthand is just what heap + overhead happened to work out to at around a 1.5 GiB heap under sustained load (1,536 + 735 ≈ 1.48×). It is a reasonable floor for heaps of roughly a gigabyte or more, but it gets progressively worse as the container gets smaller: the fixed overhead stays roughly the same while the heap shrinks, so the effective multiple climbs and a larger fraction of the container goes to memory the percentage cap cannot bound. Do not extrapolate 1.5× down to a small container — and note the 735 MiB itself is a conservative upper bound (the measurement run carried profiling instrumentation, which uses native memory) that rises further with more concurrent connections and larger bodies. The heap the 45% cap gives you, and what that leaves for the overhead, at common container sizes:

The “left for non-heap + native” column is simply limit − heap — the budget the percentage cap leaves for everything -Xmx does not count. Compare it against the overhead your traffic actually produces: the ~735 MiB measured is for one sustained-load profile and grows with concurrency and body size (the same effect that makes 1.5× a floor, not a constant). A container is safe when this column comfortably exceeds your measured overhead — which is why 2 GiB is recommended at high request rates and 512 MiB is a floor, not a target. To size for your own workload, watch container RSS or enable CSV memory tracking (see Monitoring Memory Usage below) under representative load rather than trusting a multiple of the heap; and when in doubt, give the non-heap side room, because it is the part the heap-percentage cap cannot bound.

If your container is killed with exit code 137. When the total footprint exceeds the container limit, the Linux kernel kills the process — the container exits with code 137 and OOMKilled: true, and there is no Java stack trace and no OutOfMemoryError in the logs, because the JVM did not fail — it was killed from outside. Confirm it with:

docker inspect --format '{% raw %}{{json .State}}{% endraw %}' <container>
# "OOMKilled": true, "ExitCode": 137

The fix is a larger memory limit or a smaller heap percentage — not a bigger heap. Seeing 137 with plenty of -Xmx headroom is the classic trap: raising -Xmx makes it worse, because the heap was never the whole footprint. Either raise --memory to cover the heap plus the load-driven overhead above, or lower the cap.

Off-heap buffer limit. Whenever MockServer runs as its own process (the Docker images, the standalone jar, the forked Maven plugin and the launchers), the off-heap buffers Netty uses for request and response bodies are limited to a quarter of the maximum heap, and at least 64 MiB. At the images' default heap that is 64 MiB in a 512 MiB container and 115 MiB in a 1 GiB one. Without the limit these buffers could grow as large as the heap itself, and the container could be killed with exit code 137. What counts against it:

  • Large downloads by slow clients count very little. MockServer sends a large response a slice at a time as the client reads it, so each such client holds about 64 KB.
  • Forwarded and proxied responses are held in full while MockServer collects them, and so are request bodies while they are being uploaded. Several large forwards or uploads at once can reach the limit: at 64 MiB, one forwarded 49 MiB response succeeds, but two at the same time both fail.
  • Responses through a CONNECT or SOCKS tunnel are also held in full on their way to the client.

When the limit is reached, whichever connection needs a buffer next is closed — which may be an unrelated request, not the one holding the memory — and MockServer keeps serving everything else. A client whose request was being forwarded gets a 502 response; a client whose own connection was the one closed sees the connection drop (for example a connection reset, or an incomplete upload). The log shows direct memory limit (io.netty.maxDirectMemory) reached. If your traffic needs more, raise the limit with -XX:MaxDirectMemorySize or -Dio.netty.maxDirectMemory=<bytes> — in Docker, through JAVA_TOOL_OPTIONS, keeping the image's -XX:+UseZGC, for example -e JAVA_TOOL_OPTIONS="-XX:+UseZGC -XX:MaxDirectMemorySize=256m". MockServer leaves either setting as you set it, and logs the limit in effect at start-up in a line beginning netty direct memory limit. Leave room for the limit in the container on top of the heap.

Overriding the default, and what you trade. The 45% cap only applies when you have not set an explicit heap. To change it you have two levers, and it is important not to confuse them:

  • To use a different percentage of the container limit, rebuild or re-run so the JVM sees a different -XX:MaxRAMPercentage. Note the footgun: passing a different -XX:MaxRAMPercentage via JAVA_TOOL_OPTIONS does not work — the image's entrypoint applies its own value last, so it always wins.
  • To pin an absolute heap size, set an explicit -Xmx via JAVA_TOOL_OPTIONS. Be aware that setting -Xmx (or any heap sizing via JAVA_TOOL_OPTIONS) disables MaxRAMPercentage entirely — the percentage cap no longer applies at all. A user who sets one thinking it tunes the other gets neither, so choose one mechanism, and still size the container against the heap plus the load-driven overhead above — not a fixed multiple of the heap:
docker run -d --rm -p 1080:1080 \
  -e JAVA_TOOL_OPTIONS="-XX:+UseZGC -Xmx512m" \
  mockserver/mockserver

When running with docker compose:

services:
  mockServer:
    image: mockserver/mockserver
    ports:
      - "1080:1080"
    environment:
      JAVA_TOOL_OPTIONS: "-XX:+UseZGC -Xmx512m"
      MOCKSERVER_MAX_LOG_ENTRIES: "5000"

When running as a standalone JAR:

java -Xmx512m -jar mockserver-netty.jar -serverPort 1080

How large bodies affect this choice. Whether -Xmx512m is adequate depends entirely on the bodies your traffic carries. Under sustained load at the default INFO log level, a 512 MB heap handled 1 KB request bodies — 200,000 requests served with peak heap at 479 of 512 MB. With the ring buffer’s in-flight bytes now bounded by an in-flight cap (a seventh of the heap ceiling, a twelfth at DEBUG /TRACE), larger bodies survive too: at INFO with 256 KB bodies, all 200,000 requests completed (peak 443 MB); at INFO with 64 KB bodies, all 200,000 requests completed. These runs were measured on earlier September 2026 builds whose INFO budget was larger than today's default of a twentieth of the heap ceiling (a quarter for the 1 KB run, an eighth for the 64 KB and 256 KB runs), and before later fixes to how completely the budget counts each entry, so the log held more memory in those runs than the current default allows. They were measured with a single expectation — a best case that generates roughly three log entries per request. A suite with many expectations generates more log entries per request and will exhaust the ring sooner, so treat these as upper bounds, not floors.

Why it now survives, and what happens under extreme pressure. The previous failure path was the LMAX Disruptor ring: requests were published to it holding their full body, and the byte budget only applied after an entry was consumed into the deque. At INFO, the consumer is slow (it formats every entry to system-out), so the ring backed up with full bodies before the budget could apply — exhausting the heap before any eviction ran. The ring’s in-flight bytes are now bounded too, by the larger of maxEventLogSizeInBytes and a heap-derived cap (a seventh of the heap ceiling, a twelfth at DEBUG /TRACE): once body bytes waiting in the ring would exceed it, new entries are dropped rather than admitted. A second inflation source has also been eliminated: previously, each JSON-body entry was retaining a parsed Jackson node tree roughly five times its raw body size for its whole life in the deque, but the weigher counted only the raw bytes — so a server told to hold 256 MB of bodies could hold well over a gigabyte and die of heap exhaustion while the budget believed it had room. Those trees are now built transiently at render time only and are not retained on the entry: measured on 20,000 retained entries, actual heap dropped from 429 MB to 61 MB with bodies unchanged. The budget therefore now tracks retained memory far more closely. The weigher was also made honest about the memory each entry holds beyond its body: it now counts the header bytes and a fixed per-entry overhead for the log entry and each request/response object it retains, not the raw body bytes alone. Measured on live heaps, this brought real retention from about 2.6× the budget at WARN and 4.8× at INFO down to about 2× and 3×. Later fixes removed the remaining copies of each body that the budget could not see (the decoded string kept alongside the raw bytes, and extra copies held by forwarded and templated-echo entries). Re-measured in September 2026 under both the G1 and ZGC garbage collectors, real retention is now 0.50–0.80× the counted budget at WARN and 1.04–2.03× at INFO once the log has caught up, rising to 0.97× and 2.31× when the server receives more traffic than it can log. The entries still waiting to be logged, which hold up to another 0.72× of their cap, are capped separately, and the default divisors are set so both parts together stay at or below about a quarter of the heap ceiling. That INFO gap was the formatted log message, which embeds the body as text; an entry that quotes a request or response no longer keeps it, and re-measured in October 2026 kept entries at INFO held 0.70–1.00× their counted size on JSON and proxy traffic, so the waiting-entries cap at INFO is now the same seventh of the heap ceiling as at WARN; DEBUG and TRACE were not re-measured and keep a twelfth. Because the old accounting under-counted, the same maxEventLogSizeInBytes value now retains fewer entries — the budget evicts sooner, which is the bound doing what it claims; raise it if you relied on the previous, larger retention for a given budget. Size against the multiple, not the budget alone, and measure against your own workload — the multiple depends on how large your bodies and headers are. Under enough sustained pressure MockServer drops entries rather than dying — drops are not silent: a once-only WARN is logged on the first drop, the mock_server_dropped_log_events Prometheus counter increments under the label reason="in_flight_bytes" (drops because the logging thread fell behind are labelled reason="ring_full"), and the dashboard's log-pressure banner says which kind of drop happened and what to change. A dropped entry is a lost record: a verify with an upper bound (never(), atMost(n), exactly(n), once(), between(a,b)) will fail rather than pass once entries have been dropped — the same fail-closed treatment eviction already has. Resetting the log, or clearing it entirely (a filtered clear(request) does not reset the taint), rearms the warn-once latch and resets the drop taint. Running at WARN still helps against drops: the cap on entries waiting to be logged is heap/7 at WARN /ERROR /OFF and INFO and heap/12 at DEBUG /TRACE, and WARN drains it faster by skipping per-entry formatting. It is not a prerequisite for survival on a 512 MB heap, but it remains the cheapest lever. Note that the default kept history is smaller at WARN (heap/20, against heap/12 at INFO), because WARN is where throughput is high enough for long-lived entries to slow the garbage collector; an unrendered entry costs up to about 1× its counted bytes in the measured runs against up to about 2.3× rendered, so if you raise maxEventLogSizeInBytes at WARN you get more history for the same real heap than at INFO.

maxLoggedBodyBytes has a different, narrower role: it limits how many bytes of each body are stored in the deque, reducing the deque's steady-state footprint and what the dashboard displays. It pairs well with disk capture (persistRecordedRequestsToDisk), which writes the full body before truncation runs and keeps the complete record on disk. Important: setting maxLoggedBodyBytes breaks verification against request or response body content — a verify that matches on body returns a 406 against a truncated entry where the original body would return a 202. Verification by path, method, and header is not affected. The truncation is visible in the retrieved entry and in the dashboard via the x-mockserver-body-truncated: <originalLength> header on the stored copy. It does not prevent ring-backlog drops: maxLoggedBodyBytes truncation runs in the consumer, downstream of the ring, so the body is already in the ring at full size before truncation can run. Use it to manage the deque’s body footprint when disk capture holds the full record, not as a substitute for the byte budget.

Proxying LLM / Large-Body Traffic Without OOM

TL;DR: enable disk capture so every exchange is durable, and set a byte budget so the in-memory log stays bounded. Memory never grows unbounded; disk holds the complete session history.

When MockServer proxies LLM traffic — tool schemas, growing conversation context, SSE chunk accumulation — individual request/response bodies can be hundreds of kilobytes each. The in-memory event log is normally bounded only by entry count (maxLogEntries), not by body size, so even a few thousand LLM exchanges can exhaust the heap.

Two complementary settings address this:

Setting What it does When to use
maxEventLogSizeInBytes Caps the total request+response body bytes held in memory. Once exceeded, the oldest entries are evicted (oldest-first), in addition to the entry-count bound. Always, when proxying traffic with large bodies. Set it well under the JVM heap — for a 2 GB heap, 256 MB (268435456) is a good starting point.
persistRecordedRequestsToDisk Appends every proxied exchange — full request and response — as a single NDJSON line to a file, written to disk in small batches as soon as MockServer catches up with its log. The file is the durable record: entries evicted from the in-memory window are never lost from disk (a hard kill can lose only the last few KB of recent lines). Always paired with maxEventLogSizeInBytes. The disk write happens before any in-memory truncation, so the archive is always full-fidelity.

Recommended combo for LLM / large-body capture:

java -Xmx2g \
  -Dmockserver.maxLogEntries=5000 \
  -Dmockserver.maxEventLogSizeInBytes=268435456 \
  -Dmockserver.persistRecordedRequestsToDisk=true \
  -Dmockserver.persistedRecordedRequestsPath=recordedRequests.ndjson \
  -jar mockserver-netty.jar -serverPort 1080

With this configuration:

  • Every proxied exchange is written to recordedRequests.ndjson in full as it completes
  • The in-memory log retains at most the most recent 256 MB of body bytes (plus up to 5,000 entries by count) — the dashboard shows this recent window
  • Older entries evicted from memory are still on disk — nothing is lost

The mockserver-ui/scripts/launch-with-llm-capture.sh script uses exactly this combination by default (2 GB heap, 256 MB byte budget, NDJSON disk capture). Run it with a tool name to start MockServer as an HTTPS proxy capturing that tool's LLM traffic:

./mockserver-ui/scripts/launch-with-llm-capture.sh opencode

Optional secondary valve — maxLoggedBodyBytes: when set to a positive value, bodies are truncated in memory beyond that many bytes (the in-memory copy gets a x-mockserver-body-truncated: <originalLength> header). The disk write is not affected, so the NDJSON archive always holds the full body. Use this only when you want the dashboard to show abbreviated bodies — leave it at 0 (the default) when the byte-budget eviction (maxEventLogSizeInBytes) is sufficient. Be aware that enabling this setting breaks verification against request or response body content — a verify that matches on body will fail against a truncated entry (returning 406 where the full body would return 202). Verification by path, method, and header is not affected.

Security — data at rest: the recordedRequests.ndjson archive contains the full recorded request and response bodies on disk, which for proxied LLM and API traffic can include credentials (Authorization headers, API keys) and other sensitive data. The archive honours redactSecretsInLog — enable it to mask known secret headers and configured body fields in the file just as they are masked in the dashboard. Treat the file as sensitive regardless: store it on a protected volume and delete it when you are done. The capture launcher truncates it at the start of each session (unless you pass --keep-log).

How many connections the kernel may hold after completing their TCP handshake, while they wait for MockServer to accept them.

This matters when many clients connect at once — a load test ramping up, a connection pool refilling, or a fleet of containers starting together. Steady traffic over existing keep-alive connections does not touch the accept queue at all.

What a full queue looks like. The kernel does not refuse the connection — it silently drops the handshake packet, and the client retransmits after its initial timeout, typically one second on Linux. So the symptom is a median latency that jumps to around a second with no errors at all, which reads like a slow server rather than a connection limit. If you see that shape, raise this before looking anywhere else.

The OS caps this value. Your setting is reduced to the operating system's limit, so raise both together:

  • Linux: sysctl -w net.core.somaxconn=16384 (commonly 4096 by default)
  • Docker: docker run --sysctl net.core.somaxconn=16384 ... — containers get their own value, so setting it on the host is not enough
  • macOS: sysctl -w kern.ipc.somaxconn=16384

Type: int Default: 1024

Raise this deliberately, not routinely. A deeper queue lets the kernel admit connections your server may then be unable to serve, so the default acts as backpressure: the failure mode changes from slow to dead. Raise it when you have measured that connections are being dropped at the queue, and raise somaxconn with it.

How long, in milliseconds, a client connection may sit completely idle before MockServer closes it. Every open connection costs memory even when it carries no traffic (roughly 4 KB of kernel socket memory plus MockServer's own per-connection state), so clients that open keep-alive connections and never close them can slowly push a container towards its memory limit. This timeout releases them.

Only genuinely quiet connections are closed: nothing read or written for the whole timeout and nothing in progress. A connection is never closed by this timeout while it is:

  • waiting for a response — a delayed response, a slow forward, or a request paused at a breakpoint
  • streaming a response — Server-Sent Events, chunked or gRPC streaming, however long the gaps between messages
  • carrying an open HTTP/2 stream
  • a WebSocket or a raw (non-HTTP) proxied connection

A CONNECT or SOCKS proxy tunnel is treated like any other connection: it is closed, together with MockServer's own internal connection for it, once nothing has passed through it for the whole timeout and no request sent through it is waiting for its response. A tunnel with a request still being uploaded, a delayed or streamed response, or an open HTTP/2 stream is never closed by this timeout. Clients that pool proxy tunnels reconnect as they do for any idle connection closed by a server.

Exception: HTTP/1.1 requests pipelined behind a stuck response. MockServer answers pipelined HTTP/1.1 requests in order, so a request pipelined behind one MockServer is still answering is held, not counted as waiting for a response on its own account. If the response it is held behind makes no progress at all — no bytes written, no stream event — for this same timeout, MockServer closes the connection anyway, so a lost response does not hold pipelined requests open forever. Set the timeout to 0 and this exception stops closing connections too, but MockServer still logs one warning per connection after 5 minutes with no progress regardless of the timeout you set, so a stuck connection stays visible. A long deliberate delay (for example a breakpoint, or a response delayed longer than this timeout) with another request pipelined behind it is cut by this exception, and so is a streamed response whose gap between events is longer than this timeout, even though a stream on its own is never closed by this timeout (above); raise the timeout if you rely on delays or streaming gaps that long together with pipelining.

An error() action that keeps the connection open is not waiting for anything once it has sent its bytes, or if it sends none, so that connection counts as idle and is closed once the timeout passes. A CONNECT or SOCKS proxy tunnel that carried such a request is closed on the same terms.

The same goes for a response whose status code is 1xx (other than 101), such as 102 or 103: it is the whole of what the expectation sends, so nothing more is coming. Over HTTP/1.1 the connection stays open and is closed once the timeout passes. Over HTTP/2 MockServer sends the 1xx and then resets that request's stream (RST_STREAM with NO_ERROR), so the client's request fails at once instead of waiting for a final response, and the connection is closed once it has been idle for the timeout. Over HTTP/3 MockServer sends the 1xx (101 included, as HTTP/3 has no upgrade) without any body or trailers the expectation has, and then resets the stream with H3_NO_ERROR; the client may not see the 1xx before the reset. Over HTTP/2 and HTTP/3, MockServer logs one warning the first time each such expectation is used.

Mainstream HTTP clients (Java, OkHttp, Apache, Python, Node, Go) notice a server closing an idle pooled connection and open a new one, so the 5 minute default should go unnoticed by normal test suites. In rare cases a request sent at the exact moment a connection is closed may fail and need a retry, as with any server that closes idle keep-alive connections. Set it to 0 to never close idle connections, which was the behaviour before this setting existed. The value applies to connections accepted after it is changed.

Type: long Default: 300000 (5 minutes)

How long, in milliseconds, a response may wait for a client that has stopped reading it before MockServer gives up on it. A client that stops reading (a hung test, a paused debugger, a consumer that stops taking a stream) would otherwise keep what is waiting for it for as long as its connection stays open: an aggregated response up to its full size, and for a streamed response up to maxResponseBodySize plus an open connection to the upstream it is forwarded from.

When bytes of a response have been waiting for the whole timeout and the client has taken none of them, the response ends incomplete, is logged as a warning and is counted by the mock_server_response_write_stalls_total metric:

  • HTTP/1.1: the connection is closed (for a CONNECT or SOCKS tunnel, the tunnel is closed)
  • HTTP/2 (including HTTP/2 inside a CONNECT or SOCKS tunnel) and HTTP/3: only that stream is reset; other streams on the connection carry on (an HTTP/2 client that stops reading the connection altogether has the connection closed). An HTTP/2 stream that was waiting only for flow-control window held by the stalled stream is not reset before it, and gets another timeout period to receive that window once the stalled stream is reset. An HTTP/2 client counts as reading a stream only while the stream's data is actually being sent to it: flow-control frames that let no data be sent (a WINDOW_UPDATE while the connection's window is used up, or a changed initial window size) do not keep a stalled stream open. An HTTP/3 stream that has been sent little or nothing because stalled streams hold the connection's flow-control credit also gets another timeout period once such a stream is reset
  • a streamed (forwarded) response: its upstream connection is closed too

A client that keeps taking some of the response at least once per timeout period is not affected, and neither is a client waiting for a delayed or slow response, because nothing is waiting for it to read. The same applies to a WebSocket whose client stops reading the messages sent to it. The operating system sends data to a slow reader in bursts, sometimes seconds apart, so keep the timeout well above a few seconds; the 1 minute default leaves plenty of room. Set it to 0 to never cut off a stalled client, which was the behaviour before this setting existed. The value applies to connections accepted after it is changed.

Maximum number of matched requests that can be waiting at the same time for a configured delay before their response is sent. This covers a response or forward delay, globalResponseDelayMillis and chaos latency.

Each waiting request is held in memory until its delay ends, so a high request rate against a slow expectation (for example 1,000 requests per second with a 10 second delay keeps 10,000 requests waiting) can use a lot of heap. When the limit is reached, further requests are answered straight away with 503 Service Unavailable and a Retry-After: 1 header instead of being held, so the server stays healthy.

A request answered this way has still matched its expectation: it counts towards the expectation's times (so a once() expectation is used up), may have used a rate-limit allowance, and has no response entry in the request log. A forwarded response that is waiting only for chaos latency is sent immediately without the latency instead of being refused, because the upstream has already been called.

Delayed side actions (after-actions, secondary actions and step side effects) have a separate allowance of the same size. When it is full further ones are skipped and logged, so they never cause a 503.

Delayed replies of a two-way (bidirectional) WebSocket mock have a third allowance of the same size, counted in reply messages. A reply to one incoming message is always sent completely or not at all: when the allowance is full, the WebSocket is closed with status 1013 (Try Again Later) and none of that reply is sent. Before that point, a single connection with more than 128 delayed replies still waiting simply stops being read until they drain, which slows a fast client down instead of failing it.

Rejections are reported in a WARN log line at most every 10 seconds and, when metrics are enabled (metricsEnabled), counted by the mock_server_overload_rejections metric (with reason delayed_responses, delay_skipped, side_actions or websocket_replies); the mock_server_pending_delayed_tasks metric shows how many are currently waiting.
