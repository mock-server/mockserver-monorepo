Memory Tuning Guide

MockServer stores expectations and log entries in memory using ring buffers. The two most important settings that affect memory usage are maxExpectations and maxLogEntries. Each HTTP request processed by MockServer generates 2-3 log entries (the request itself, the expectation match result, and the response). Because maxLogEntries caps the entry count and cannot see how large each entry is, a workload with large bodies is bounded instead by maxEventLogSizeInBytes — a byte budget that is on by default, sized so real retained heap is about a quarter of the heap ceiling so a few large bodies cannot exhaust the heap through a count-only cap.

Both settings have automatic defaults derived from the JVM heap size (the -Xmx maximum), so the default is the same for every MockServer instance in a JVM regardless of how much memory is already in use. The table below provides recommended values if you want to override the defaults for different heap sizes:

JVM Heap Size maxExpectations maxLogEntries Approx HTTP Requests Retained
256 MB 1,000 5,000 ~1,500 - 2,500
512 MB 2,000 15,000 ~5,000 - 7,500
1 GB 5,000 40,000 ~13,000 - 20,000

These are conservative estimates assuming typical request/response sizes of 1-5 KB. Large request or response bodies will consume more memory per entry.

Tips for reducing memory usage:

  • Reduce maxLogEntries to limit the number of stored request/response log entries
  • Reduce maxExpectations if expectations contain large response bodies
  • Increase JVM heap size (-Xmx) to give the garbage collector more headroom
  • Use outputMemoryUsageCsv to monitor actual heap usage and tune values accordingly

Docker example with memory-constrained settings:

docker run -d --rm -p 1080:1080 \
  --env MOCKSERVER_MAX_EXPECTATIONS=1000 \
  --env MOCKSERVER_MAX_LOG_ENTRIES=5000 \
  mockserver/mockserver

Troubleshooting: MockServer Becomes Slow or Unresponsive

If MockServer appears to freeze, hang, or become progressively slower under sustained load, the most likely cause is memory pressure from log entry accumulation. This section explains why it happens and how to fix it.

If instead connections are being refused or failing to open, this is not the section you want. Two errors in particular are operating-system limits rather than MockServer, and neither is fixed by any MockServer setting:

  • Too many open files, or Netty's ChannelException: Unable to create Channel — the process has run out of file descriptors, one of which every connection needs. On macOS the JVM caps this at 10,240 however high you set ulimit -n, and the fix differs between macOS and Linux.
  • Can't assign requested address / BindException — the client machine has run out of ephemeral source ports. This one is never the server.

See Concurrent connection limits are set by the OS and the JVM for the cause of each and what to change.

Why Does MockServer Slow Down?

Every HTTP request that MockServer processes generates 2-3 log entries that are stored in memory regardless of the configured log level. These entries record the received request, expectation match result, and response — they are always stored to support request verification. Each log entry consumes approximately 4-10 KB of heap for small request/response bodies, scaling proportionally for larger bodies. Under sustained high-throughput load, log entry allocation drives significant GC pressure:

Request Rate Response Body Size Log Data Generated Per Minute
1 req/s 1 KB ~1 MB
10 req/s 1 KB ~12 MB
10 req/s 100 KB ~120 MB
1 req/s 1 MB+ ~120 MB

Log entries are stored in a bounded circular queue (maxLogEntries), so total memory usage does not grow indefinitely. However, the constant allocation and eviction of log entries creates GC pressure. When the JVM heap fills up, the garbage collector runs more frequently and for longer, causing pauses that make MockServer appear to freeze. In extreme cases, the JVM may spend almost all of its time in garbage collection, effectively halting request processing.

Large response bodies amplify this problem significantly. A single expectation returning a 10 MB response at 1 request per second generates over 600 MB of log data per minute — far more than a default heap can handle. Even with ring buffer eviction, the JVM must allocate and then garbage-collect these large objects continuously.

Note: Expectations with large response bodies also consume heap proportionally (e.g., a 50 KB response body results in ~55-75 KB per stored expectation). If you have many expectations with large bodies, reduce maxExpectations as well.

How To Fix It

Apply one or more of the following, depending on your use case:

Fix When To Use Trade-off
Increase JVM heap size Always recommended for large responses or high request rates Uses more container/host memory
Reduce maxLogEntries The single most effective fix — fewer entries means less memory and less GC pressure Fewer requests available for verification
Reduce maxExpectations When expectations contain large response bodies Fewer expectations can be stored simultaneously
Switch to ZGC (-XX:+UseZGC) Heap ≥ 4 GB and matcher latency matters — typically gives single-digit-millisecond GC pauses where G1 commonly sits in the 50–200 ms range under sustained allocation Fixed memory overhead (less attractive below ~4 GB); set -Xms and -Xmx to the same value (e.g. -Xms4g -Xmx4g) so the heap is pre-committed

Note on GC selection: Java 17 makes ZGC production-ready in every JDK distribution MockServer supports. For deployments with deep ring buffers (high maxLogEntries) or large heaps, -XX:+UseZGC can reduce p99 matcher latency by holding stop-the-world pauses to the single-digit-millisecond range (typically 1–5 ms in Java 17's non-generational ZGC). For small-fixture deployments (a sidecar in a test pipeline), the default GC is fine — ZGC's fixed overhead isn't worth it below ~4 GB heap. In containerised deployments using ZGC, size the container memory limit at ~1.5× your -Xmx value to leave headroom for JVM overhead (code cache, metaspace, thread stacks) and Netty's direct buffer pool. Note that ZGC multi-maps the same physical pages for its coloured-pointer scheme; under some cgroup RSS-accounting modes those pages are counted multiple times against the container limit, so the process can be OOM-killed even though the actual physical footprint fits (e.g. -Xmx4g → --memory=6g). Shenandoah is not recommended — it is not available in Oracle JDK 17 and not universally available across all JDK distributions, so ZGC is the simpler choice.

Note on logLevel and disableLogging: the received-request and response log entries — the ones a verify reads — are always stored regardless of log level, so lowering the level never breaks verification. But the per-expectation match / did-not-match diagnostic entries are stored only at INFO or more verbose: at WARN they are neither produced nor retained. So on a workload with many expectations, running at WARN genuinely reduces the number of entries retained per request (a request that scans N expectations before matching can log up to N diagnostic entries at INFO), which lowers memory and eviction pressure without affecting what verify can find — the cheapest safe lever when a memory-constrained server is under load. It does not reduce the memory held by large request/response bodies, which are on the always-retained entries; for those, the byte budget (maxEventLogSizeInBytes, on by default) bounds both the ring's in-flight backlog and the deque — at INFO the server now drops entries rather than OOM-ing when the budget is reached (see the heap-sizing section below). WARN widens the budget by half again (the default is log-level-aware) and drains the ring faster, so it remains the cheapest lever for large-body workloads. maxLoggedBodyBytes (per-entry body truncation) reduces the deque's steady-state body footprint — truncation runs in the consumer, after the ring, so it does not reduce the ring's in-flight byte contribution — and breaks verification against body content — a verify that matches on body will fail against a truncated entry; verification by path, method, and header is unaffected. disableLogging only suppresses system-out output and does not reduce memory usage.

Note on logLevel and matching throughput: beyond the retained-entry saving above, running below INFO also cuts transient per-request allocation on the matching hot path. At INFO, every request that scans expectations builds and logs a diagnostic “matched”/“did not match because…” message per matcher; below INFO that work — the per-matcher log entry and the human-readable “because” string assembly — is skipped entirely. For a deployment with many expectations under sustained load this is the single largest matching-path allocation, so running at WARN noticeably cuts allocation churn and GC pressure (it does not change which requests match, only whether the diagnostic narrative is produced). Lowering the level therefore helps on two fronts — fewer retained diagnostic entries (memory) and less transient allocation (throughput/GC) — while leaving the received-request/response entries that verify depends on fully intact.

Recommended Configurations

High-throughput with small responses (e.g., API mocking at >10 req/s with <10 KB bodies):

docker run -d --rm -p 1080:1080 \
  -e MOCKSERVER_MAX_LOG_ENTRIES=5000 \
  mockserver/mockserver

Large response bodies (e.g., responses >100 KB):

docker run -d --rm -p 1080:1080 \
  -e JAVA_TOOL_OPTIONS="-Xmx1g" \
  -e MOCKSERVER_MAX_LOG_ENTRIES=1000 \
  -e MOCKSERVER_MAX_EXPECTATIONS=100 \
  mockserver/mockserver

Maximum throughput, minimal memory (verification limited to most recent requests):

docker run -d --rm -p 1080:1080 \
  -e JAVA_TOOL_OPTIONS="-Xmx512m" \
  -e MOCKSERVER_MAX_LOG_ENTRIES=100 \
  -e MOCKSERVER_LOG_LEVEL=WARN \
  mockserver/mockserver

MOCKSERVER_LOG_LEVEL=WARN drops the per-matcher diagnostic logging on the matching hot path (see the note above), which is the largest matching-path allocation when many expectations are registered. If your matchers rely heavily on regular expressions and your patterns and inputs are trusted, also add -e MOCKSERVER_REGEX_MATCHING_TIMEOUT_MILLIS=0 to evaluate regexes inline and skip the per-regex thread hand-off (this removes the catastrophic-backtracking guard — see Regex Matching Timeout).

Configuring JVM Heap Size

The MockServer Docker image caps the JVM heap at 60% of the container's memory limit (-XX:MaxRAMPercentage=60.0), so the in-memory ring buffers size off a bounded heap. Always run the container with an explicit memory limit (for example --memory=2g, or resources.limits.memory in Kubernetes) — without one the JVM sizes its heap off the host's total memory, and the default ring sizes (maxLogEntries and maxExpectations, which derive from available heap) scale up with it, so MockServer can be OOM-killed under load.

Sizing the container for your workload. The heap is only part of what the Java process occupies, and — this is the part that trips people up — the rest is not a fixed fraction of the heap. It is largely additive and driven by load, not by heap size. Under sustained load a 1,536 MiB heap was measured occupying 2,271 MiB of real memory; the 735 MiB difference breaks down as:

  • class metadata (metaspace) and the JIT code cache — about 133 MiB, and roughly constant regardless of heap;
  • one stack per thread — tens of MiB, set by the thread count (which tracks CPU cores), not the heap;
  • the garbage collector's own bookkeeping — this part does scale with the heap;
  • and the largest, most variable piece: the pool of direct (off-heap) network buffers Netty uses for request and response bodies, whose size is driven by concurrency and body size and not by the heap at all.

None of that is counted by -Xmx, and most of it does not shrink when you shrink the heap. So the practical model is footprint ≈ heap + overhead, where the overhead is dominated by heap-independent, load-driven terms. A 75% cap could not fit — at 75% of a 2 GiB limit the heap alone (1,536 MiB) plus this overhead exceeded the limit and the kernel killed the process — which is why the default is 60%.

The convenient “budget about 1.5× the heap” shorthand is just what heap + overhead happened to work out to at around a 1.5 GiB heap under sustained load (1,536 + 735 ≈ 1.48×). It is a reasonable floor for heaps of roughly a gigabyte or more, but it gets progressively worse as the container gets smaller: the fixed overhead stays roughly the same while the heap shrinks, so the effective multiple climbs and a larger fraction of the container goes to memory the percentage cap cannot bound. Do not extrapolate 1.5× down to a small container — and note the 735 MiB itself is a conservative upper bound (the measurement run carried profiling instrumentation, which uses native memory) that rises further with more concurrent connections and larger bodies. The heap the 60% cap gives you, and what that leaves for the overhead, at common container sizes:

Container memory limit Heap at the 60% default Left for non-heap + native Realistic use
512 MiB~307 MiB~205 MiBLight use only — low concurrency, bodies up to a few KB. Under load like the measurement (~700+ MiB of overhead) this is the size most likely to be OOM-killed, not the safest.
1 GiB~614 MiB~410 MiBModerate load and body sizes.
2 GiB~1229 MiB~819 MiBComfortably above the ~735 MiB of overhead measured under sustained load — the smallest size proven safe at high request rates.
4 GiB~2458 MiB~1638 MiBHigh concurrency and/or large bodies.

The “left for non-heap + native” column is simply limit − heap — the budget the percentage cap leaves for everything -Xmx does not count. Compare it against the overhead your traffic actually produces: the ~735 MiB measured is for one sustained-load profile and grows with concurrency and body size (the same effect that makes 1.5× a floor, not a constant). A container is safe when this column comfortably exceeds your measured overhead — which is why 2 GiB works at high request rates and 512 MiB does not. To size for your own workload, watch container RSS or enable CSV memory tracking (see Monitoring Memory Usage below) under representative load rather than trusting a multiple of the heap; and when in doubt, give the non-heap side room, because it is the part the heap-percentage cap cannot bound.

If your container is killed with exit code 137. When the total footprint exceeds the container limit, the Linux kernel kills the process — the container exits with code 137 and OOMKilled: true, and there is no Java stack trace and no OutOfMemoryError in the logs, because the JVM did not fail — it was killed from outside. Confirm it with:

docker inspect --format '{{json .State}}' <container>
# "OOMKilled": true, "ExitCode": 137

The fix is a larger memory limit or a smaller heap percentage — not a bigger heap. Seeing 137 with plenty of -Xmx headroom is the classic trap: raising -Xmx makes it worse, because the heap was never the whole footprint. Either raise --memory to cover the heap plus the load-driven overhead above, or lower the cap.

Overriding the default, and what you trade. The 60% cap only applies when you have not set an explicit heap. To change it you have two levers, and it is important not to confuse them:

  • To use a different percentage of the container limit, rebuild or re-run so the JVM sees a different -XX:MaxRAMPercentage. Note the footgun: passing a different -XX:MaxRAMPercentage via JAVA_TOOL_OPTIONS does not work — the image's entrypoint applies its own value last, so it always wins.
  • To pin an absolute heap size, set an explicit -Xmx via JAVA_TOOL_OPTIONS. Be aware that setting -Xmx (or any heap sizing via JAVA_TOOL_OPTIONS) disables MaxRAMPercentage entirely — the percentage cap no longer applies at all. A user who sets one thinking it tunes the other gets neither, so choose one mechanism, and still size the container against the heap plus the load-driven overhead above — not a fixed multiple of the heap:
docker run -d --rm -p 1080:1080 \
  -e JAVA_TOOL_OPTIONS="-Xmx512m" \
  mockserver/mockserver

When running with docker compose:

services:
  mockServer:
    image: mockserver/mockserver
    ports:
      - "1080:1080"
    environment:
      JAVA_TOOL_OPTIONS: "-Xmx512m"
      MOCKSERVER_MAX_LOG_ENTRIES: "5000"

When running as a standalone JAR:

java -Xmx512m -jar mockserver-netty.jar -serverPort 1080

How large bodies affect this choice. Whether -Xmx512m is adequate depends entirely on the bodies your traffic carries. Under sustained load at the default INFO log level, a 512 MB heap handled 1 KB request bodies — 200,000 requests served with peak heap at 479 of 512 MB. With the ring buffer’s in-flight bytes now bounded by the same byte budget (maxEventLogSizeInBytes), larger bodies survive too: at INFO with 256 KB bodies, all 200,000 requests completed (peak 443 MB); at INFO with 64 KB bodies, all 200,000 requests completed. These counts were measured with a single expectation — a best case that generates roughly three log entries per request. A suite with many expectations generates more log entries per request and will exhaust the ring sooner, so treat these as upper bounds, not floors.

Why it now survives, and what happens under extreme pressure. The previous failure path was the LMAX Disruptor ring: requests were published to it holding their full body, and the byte budget only applied after an entry was consumed into the deque. At INFO, the consumer is slow (it formats every entry to system-out), so the ring backed up with full bodies before the budget could apply — exhausting the heap before any eviction ran. The ring’s in-flight bytes are now bounded by the same maxEventLogSizeInBytes budget: once body bytes waiting in the ring would exceed it, new entries are dropped rather than admitted. A second inflation source has also been eliminated: previously, each JSON-body entry was retaining a parsed Jackson node tree roughly five times its raw body size for its whole life in the deque, but the weigher counted only the raw bytes — so a server told to hold 256 MB of bodies could hold well over a gigabyte and die of heap exhaustion while the budget believed it had room. Those trees are now built transiently at render time only and are not retained on the entry: measured on 20,000 retained entries, actual heap dropped from 429 MB to 61 MB with bodies unchanged. The budget therefore now tracks retained memory far more closely. The weigher was also made honest about the memory each entry holds beyond its body: it now counts the header bytes and a fixed per-entry overhead for the log entry and each request/response object it retains, not the raw body bytes alone. Measured on a live heap dump of 20,000 retained entries, this brings real retention from about 2.6× the budget down to about 2.0× at WARN, and from about 4.8× down to about 3.0× at INFO (re-measured on live heaps in September 2026; a decoded text body is retained twice — the decoded string and the raw bytes — but counted once, which is why the WARN figure is 2.0× rather than the 1.0× an earlier binary-body measurement suggested) (the remaining INFO gap is the formatted log message, which embeds the body as text and is cached on the entry only at a rendering log level — the default budget is already tighter at INFO to cover it). Because the old accounting under-counted, the same maxEventLogSizeInBytes value now retains fewer entries — the budget evicts sooner, which is the bound doing what it claims; raise it if you relied on the previous, larger retention for a given budget. Size against the multiple, not the budget alone, and measure against your own workload — the multiple depends on how large your bodies and headers are. Under enough sustained pressure MockServer drops entries rather than dying — drops are not silent: a once-only WARN is logged on the first drop, and the mock_server_dropped_log_events Prometheus counter increments. A dropped entry is a lost record: a verify with an upper bound (never(), atMost(n), exactly(n), once(), between(a,b)) will fail rather than pass once entries have been dropped — the same fail-closed treatment eviction already has. Resetting the log, or clearing it entirely (a filtered clear(request) does not reset the taint), rearms the warn-once latch and resets the drop taint. Running at WARN still helps: the default byte budget is log-level-aware (heap/12 at INFO /DEBUG /TRACE, heap/8 at WARN /ERROR /OFF), so WARN widens the counted body budget by half again (a twelfth of the ceiling to an eighth) and drains the ring faster by skipping per-entry formatting. It is not a prerequisite for survival on a 512 MB heap, but it remains the cheapest lever — and because a rendered entry also costs 3.0× its counted bytes against 2.0× unrendered, the real-heap gain is larger than the budget change alone suggests.

maxLoggedBodyBytes has a different, narrower role: it limits how many bytes of each body are stored in the deque, reducing the deque's steady-state footprint and what the dashboard displays. It pairs well with disk capture (persistRecordedRequestsToDisk), which writes the full body before truncation runs and keeps the complete record on disk. Important: setting maxLoggedBodyBytes breaks verification against request or response body content — a verify that matches on body returns a 406 against a truncated entry where the original body would return a 202. Verification by path, method, and header is not affected. The truncation is visible in the retrieved entry and in the dashboard via the x-mockserver-body-truncated: <originalLength> header on the stored copy. It does not prevent ring-backlog drops: maxLoggedBodyBytes truncation runs in the consumer, downstream of the ring, so the body is already in the ring at full size before truncation can run. Use it to manage the deque’s body footprint when disk capture holds the full record, not as a substitute for the byte budget.

Monitoring Memory Usage

To diagnose memory issues, enable CSV memory tracking:

docker run -d --rm -p 1080:1080 \
  -e MOCKSERVER_OUTPUT_MEMORY_USAGE_CSV=true \
  -e MOCKSERVER_MEMORY_USAGE_CSV_DIRECTORY=/config \
  -v $(pwd):/config \
  mockserver/mockserver

This creates a memoryUsage_<date>.csv file that records heap usage, log entry count, and expectation count over time. If you see heap usage consistently near the maximum, increase -Xmx or reduce maxLogEntries.

 

Proxying LLM / Large-Body Traffic Without OOM

TL;DR: enable disk capture so every exchange is durable, and set a byte budget so the in-memory log stays bounded. Memory never grows unbounded; disk holds the complete session history.

When MockServer proxies LLM traffic — tool schemas, growing conversation context, SSE chunk accumulation — individual request/response bodies can be hundreds of kilobytes each. The in-memory event log is normally bounded only by entry count (maxLogEntries), not by body size, so even a few thousand LLM exchanges can exhaust the heap.

Two complementary settings address this:

Setting What it does When to use
maxEventLogSizeInBytes Caps the total request+response body bytes held in memory. Once exceeded, the oldest entries are evicted (oldest-first), in addition to the entry-count bound. Always, when proxying traffic with large bodies. Set it well under the JVM heap — for a 2 GB heap, 256 MB (268435456) is a good starting point.
persistRecordedRequestsToDisk Appends every proxied exchange — full request and response — as a single NDJSON line to a file, flushed immediately. The file is the durable record: entries evicted from the in-memory window are never lost from disk. Always paired with maxEventLogSizeInBytes. The disk write happens before any in-memory truncation, so the archive is always full-fidelity.

Recommended combo for LLM / large-body capture:

java -Xmx2g \
  -Dmockserver.maxLogEntries=5000 \
  -Dmockserver.maxEventLogSizeInBytes=268435456 \
  -Dmockserver.persistRecordedRequestsToDisk=true \
  -Dmockserver.persistedRecordedRequestsPath=recordedRequests.ndjson \
  -jar mockserver-netty.jar -serverPort 1080

With this configuration:

  • Every proxied exchange is written to recordedRequests.ndjson in full as it completes
  • The in-memory log retains at most the most recent 256 MB of body bytes (plus up to 5,000 entries by count) — the dashboard shows this recent window
  • Older entries evicted from memory are still on disk — nothing is lost

The mockserver-ui/scripts/launch-with-llm-capture.sh script uses exactly this combination by default (2 GB heap, 256 MB byte budget, NDJSON disk capture). Run it with a tool name to start MockServer as an HTTPS proxy capturing that tool's LLM traffic:

./mockserver-ui/scripts/launch-with-llm-capture.sh opencode

Optional secondary valve — maxLoggedBodyBytes: when set to a positive value, bodies are truncated in memory beyond that many bytes (the in-memory copy gets a x-mockserver-body-truncated: <originalLength> header). The disk write is not affected, so the NDJSON archive always holds the full body. Use this only when you want the dashboard to show abbreviated bodies — leave it at 0 (the default) when the byte-budget eviction (maxEventLogSizeInBytes) is sufficient. Be aware that enabling this setting breaks verification against request or response body content — a verify that matches on body will fail against a truncated entry (returning 406 where the full body would return 202). Verification by path, method, and header is not affected.

Security — data at rest: the recordedRequests.ndjson archive contains the full recorded request and response bodies on disk, which for proxied LLM and API traffic can include credentials (Authorization headers, API keys) and other sensitive data. The archive honours redactSecretsInLog — enable it to mask known secret headers and configured body fields in the file just as they are masked in the dashboard. Treat the file as sensitive regardless: store it on a protected volume and delete it when you are done. The capture launcher truncates it at the start of each session (unless you pass --keep-log).

How many connections the kernel may hold after completing their TCP handshake, while they wait for MockServer to accept them.

This matters when many clients connect at once — a load test ramping up, a connection pool refilling, or a fleet of containers starting together. Steady traffic over existing keep-alive connections does not touch the accept queue at all.

What a full queue looks like. The kernel does not refuse the connection — it silently drops the handshake packet, and the client retransmits after its initial timeout, typically one second on Linux. So the symptom is a median latency that jumps to around a second with no errors at all, which reads like a slow server rather than a connection limit. If you see that shape, raise this before looking anywhere else.

The OS caps this value. Your setting is reduced to the operating system's limit, so raise both together:

  • Linux: sysctl -w net.core.somaxconn=16384 (commonly 4096 by default)
  • Docker: docker run --sysctl net.core.somaxconn=16384 ... — containers get their own value, so setting it on the host is not enough
  • macOS: sysctl -w kern.ipc.somaxconn=16384

Type: int Default: 1024

Raise this deliberately, not routinely. A deeper queue lets the kernel admit connections your server may then be unable to serve, so the default acts as backpressure: the failure mode changes from slow to dead. Raise it when you have measured that connections are being dropped at the queue, and raise somaxconn with it.

Maximum request body size in bytes that conversation-aware LLM matchers will parse. LLM conversation matchers (whenLatestMessageContains, whenContainsToolResultFor, etc.) parse the inbound request body as JSON to extract the message history. For deep conversation histories or large tool results, this parse step is proportional to body size.

Requests whose body exceeds this cap skip conversation-aware matching and are treated as a no-match for conversation predicates (the scenario state machine is unaffected). Increase this value only when your LLM conversations regularly include very large tool results or long message histories. Reduce it in memory-constrained environments to bound the maximum allocation per matching attempt.

Type: int Default: 1048576 (1 MiB) Range: 16384 (16 KiB) — 67108864 (64 MiB)
