Service Mesh / Sidecar Configuration:

These properties configure MockServer for running as a Kubernetes sidecar with transparent proxy interception. See Transparent Proxy / Sidecar Mode for a full usage guide.

Enable transparent HTTP proxy mode where all connections are treated as proxy requests using the Host header as the forwarding target. This enables iptables REDIRECT-based interception without requiring clients to send explicit HTTP CONNECT requests or configure proxy settings.

When enabled, MockServer reads the Host header from each incoming request to determine the forwarding target. If an expectation matches, MockServer returns the mock response; otherwise it forwards to the original target.

Security: connections handled as transparent proxying are not asked for proxy credentials, even when proxyAuthenticationUsername and proxyAuthenticationPassword are set, because an intercepted client does not know it is using a proxy and cannot send them. This includes connections whose destination comes from the Host header (when the original destination cannot be found) or from a PROXY protocol header, which MockServer accepts from any client unless proxyProtocolTrustedSources is set. So any client that can reach the port can use it as a proxy without credentials. MockServer logs a warning at startup when transparent proxying and proxy credentials are both set. Only let the intercepted traffic reach a transparent-proxy port.

Type: boolean Default: false

Java Code:

Environment Variable:

MOCKSERVER_TRANSPARENT_PROXY_ENABLED=...

Property File:

Example:

-Dmockserver.transparentProxyEnabled="true"

Resolve the original destination of intercepted connections using the Linux TPROXY mechanism instead of REDIRECT. When enabled, the original destination is read from the socket's local address (preserved by the TPROXY iptables target), allowing MockServer to forward to the real destination address rather than relying on the Host header.

Requires Linux, the epoll transport, the CAP_NET_ADMIN capability, and TPROXY iptables rules instead of REDIRECT.

Type: boolean Default: false

Resolve the original destination of intercepted connections by reading from a pinned eBPF (BPF) hash map, populated by an external cgroup/connect4 BPF program and keyed by socket cookie. This is an alternative to TPROXY for recovering the real destination address.

Requires Linux, the CAP_BPF capability, a BTF-enabled kernel, and the external BPF program that populates the map (see transparentProxyEbpfMapPath).

Type: boolean Default: false

Path to the pinned BPF map used by the eBPF original destination resolver. The map must be a BPF hash map with a u64 key (socket cookie) and a 6-byte value (4-byte IPv4 address + 2-byte port in network byte order).

Only used when transparentProxyEbpf is enabled.

Type: string Default: /sys/fs/bpf/mockserver_orig_dst

The only addresses a PROXY protocol (v1 or v2) header is accepted from when transparentProxyEnabled is on: a comma-separated list of IP addresses and CIDR blocks, IPv4 or IPv6, such as 10.0.1.17 or 10.0.1.0/24. Set it to the addresses of the load balancer that adds the header, and nothing wider: the list must not include any address your clients connect from, or those clients can send their own header. Setting it is recommended whenever transparentProxyEnabled is on and clients other than the load balancer can reach MockServer.

A PROXY header tells MockServer where to forward a connection and which client address to record for it, so a client that can send its own header can choose both. With this property set, a connection from any other address that starts with a PROXY header is closed without an answer, and MockServer logs a warning (at most once a minute, with a count of the refusals since the last one); the addresses it accepts are logged at startup. Connections that send no PROXY header, including CONNECT and SOCKS tunnels, are handled as usual. The address checked is the one the connection actually comes from (its TCP peer), never one the header names. Behind a load balancer that keeps the client's address, such as an AWS NLB with instance targets or a Kubernetes service with externalTrafficPolicy: Local, the TCP peer is the end client, not the load balancer, so list only addresses that clients cannot connect from. In sidecar mode, where iptables redirects the pod's own traffic, connections come from 127.0.0.1 or the pod's IP, and trusting those trusts every process in the pod.

Empty (the default) accepts a PROXY header from any client, as before. An entry that is not a single IP address or CIDR block stops MockServer from starting: a host name, a block with bits set after its prefix (10.0.1.17/24), a block that covers every address (0.0.0.0/0, ::/0) or every IPv4 address, an address with a zone (fe80::1%eth0), an IPv4 part with a leading zero (010.0.1.17) or an IPv4 address written as ::10.0.1.17. Each entry is checked on its own, so several entries that together cover every address are not refused: keep the list to your load balancer's addresses. It is fixed at startup: a PUT /mockserver/configuration request cannot change it.
