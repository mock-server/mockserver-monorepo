Template Restriction Configuration:

Set comma separated list of the only classes javascript templates are allowed to use via Java.type(...).

By default javascript templates cannot use any Java class at all. Everything else in a template still works — the full modern JavaScript standard library is available — but Java.type(...) and the java.* globals resolve nothing until you list the classes you want here. This is deliberate: a template that can reach java.lang.Runtime can run OS commands inside the MockServer process, so anyone able to register an expectation could run code on your machine.

If one of your templates needs a Java class, add just that class (or its package). Setting this to * lets templates resolve any class again — only do that when every template you render comes from a source you fully trust.

When set, this takes precedence over javascriptDisallowedClasses. Entries match a class name exactly, or match a whole package when they end in .* (for example java.util.*).

With forwardCredentialHeadersByHost set, a template that is given any Java class may be able to read the environment variables holding those credentials, so MockServer logs a warning at startup when this setting gives templates a class, and this setting can then only be changed before MockServer starts.

Type: string Default: "" (no Java classes can be used)

Set comma separate list of classes not allowed to be used by javascript templates

Setting this widens the default: instead of "no Java class can be used", templates may then use every class except the ones you list here. That is weaker protection, because a list of banned classes can never be complete — banning java.lang.Runtime still leaves java.lang.ProcessBuilder, and a template can reach other classes indirectly. Prefer javascriptAllowedClasses above, or leave both unset.

With forwardCredentialHeadersByHost set, a template that is given any Java class may be able to read the environment variables holding those credentials, so MockServer logs a warning at startup when this setting gives templates a class, and this setting can then only be changed before MockServer starts.

Comma-separated list of literal substrings that must not appear in a JavaScript response template's source. Maximum time in milliseconds a JavaScript response template is allowed to run before it is cancelled. A runaway or malicious template (for example one containing an infinite loop) would otherwise pin the worker thread handling that request indefinitely; this cap aborts the evaluation with a clear timeout error instead, so the request fails fast and the thread is freed.

The default of 5000 (5 seconds) is far longer than any legitimate template needs — a normal template evaluates in well under a second — so it will not affect real templates. Increase it only if you run unusually heavy templates, or set it to 0 (or a negative value) to disable the timeout entirely and restore the previous unbounded behaviour.

Type: long Default: 5000

Maximum time in milliseconds a Velocity template is allowed to run. When the time is up, the template is stopped with a clear timeout error at its next #foreach iteration, macro call, #parse, #evaluate or use of a #define block, so a loop that never ends (for example over [1..2147483647], or loops nested inside each other), a recursive macro or a chain of blocks cannot keep a template thread busy until MockServer is restarted. A single slow Java call made by the template, such as a regular expression that backtracks heavily or a method that walks a very large range, cannot be stopped part-way, and the limit is on time, not memory.

The default of 5000 (5 seconds) is far longer than a normal template needs, so it will not affect real templates. Increase it only if you run unusually heavy templates, or set it to 0 (or a negative value) to remove the limit.

Type: long Default: 5000

If true (the default since 9.0.0), a response or forward template that fails (it throws an error, does not parse, hits its execution timeout, or produces output that is not a valid response or request) answers the request with 500 Internal Server Error, an x-mockserver-template-error: true header and the template error as a plain-text body, with the template line, column and a hint when the engine reports them; for output that is not valid, the body lists what is wrong with it. The same applies to the response template of a forward with overrides. If false (the default before 9.0.0) a response or forward template that throws answers 404 Not Found, which looks the same as a request that matched no expectation, a response template whose output is not a valid response also answers 404 Not Found, a forward template whose output is not a valid request answers 502 Bad Gateway, a forward's response template that fails answers 502 Bad Gateway, and a forward's response template whose output is not valid leaves the upstream response unchanged; the template error is in the log either way.

The 500 makes a template bug obvious. The body carries the template engine's error message or the validation errors, which can quote part of the template or its output, so set it to false if the callers of your mock should not see template details, or if your tests expect the 404 that MockServer answered before 9.0.0.

Type: boolean Default: true

Seed for the template faker sample-data helper (Velocity $faker, Mustache {% raw %}{{faker.*}}{% endraw %}, JavaScript faker). By default faker is unseeded, so faker-driven templates produce different, random values on every render.

Set a non-zero value to seed faker deterministically so faker-driven templates generate reproducible fixtures across runs — useful when you want your generated test data to be stable from one run to the next. The seed produces a deterministic sequence of values for a given order of renders; determinism is strongest when fixtures are generated sequentially.

The default of 0 leaves faker unseeded, so existing templates are unaffected.

The environment variables and system properties that templates can read with the systemValue helper (Velocity $systemValue.env('APP_REGION'), JavaScript systemValue.env('APP_REGION'), Mustache {% raw %}{{#systemValue.env}}APP_REGION{{/systemValue.env}}{% endraw %}, and property in place of env for a system property). This is the equivalent of WireMock's --permitted-system-keys.

Give a comma-separated list of exact names, such as APP_REGION, or prefixes ending in *, such as APP_*, which allows every name that starts with APP_. Names are case-sensitive and one list covers both environment variables and system properties. A * anywhere other than at the end, or on its own, is ignored with a warning, so you cannot allow every name.

One list covers both environment variables and system properties, so an entry such as app.* also allows an environment variable with that name (and on Windows, where environment variable names ignore case, one that differs only in case). Whatever the list says, templates can never read MockServer's own settings, which can hold passwords and keys: system properties and environment variables whose names start with mockserver. or MOCKSERVER_ (in any case), the javax.net.ssl.keyStorePassword and javax.net.ssl.trustStorePassword system properties, and the environment variables named in forwardCredentialHeadersByHost, which hold credentials for upstream hosts. An entry that names or covers them is reported with a warning when MockServer starts.

The default is empty, so systemValue returns an empty value for every name. A name that is not on the list also returns an empty value, exactly like a name that is not set, so a template cannot tell whether it exists, and a warning naming it is logged once (not on every request). There is no way for a template to list names or values.

Security: anyone who can create expectations can write a template that returns these values, so anyone who can create expectations, call them, or read the MockServer log or dashboard can read the value of every name on this list. Never list secrets such as passwords, tokens or keys, avoid broad prefixes such as java.* or javax.net.ssl.*, and prefer exact names. Each time MockServer starts with a list that is not empty, it logs a warning naming what templates can read.

This can only be set before MockServer starts (system property, environment variable, properties file or startup configuration); PUT /mockserver/configuration ignores it with a warning, so a request to the control plane cannot widen it.

Type: string Default: "" (templates read nothing)
