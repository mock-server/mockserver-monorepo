An extension is a Java class of your own that MockServer loads and starts when it starts, and stops when it stops. Extensions can only be configured at startup: the control plane (PUT /mockserver/configuration) cannot add, remove or change them, so nobody who can reach MockServer over the network can load code into it.

Extensions are trusted code. They run inside MockServer with the same access as MockServer itself, so only load extensions you wrote or trust.

When no extension is configured, MockServer loads none of the extension machinery and scans nothing, so start-up time and request handling are unchanged.

Writing an extension

Implement org.mockserver.extension.Extension, which is in mockserver-core. Add MockServer to your build with provided scope, as MockServer supplies it at runtime. A class loaded by name needs a public no-argument constructor.

package com.example;

import org.mockserver.extension.Extension;
import org.mockserver.extension.ExtensionContext;

import java.util.List;

public class AuditExtension implements Extension {

    @Override
    public String name() {
        return "audit"; // unique; lower-case letters, digits and '-'
    }

    @Override
    public void start(ExtensionContext context) {
        // runs before MockServer builds anything else; throw to refuse start-up
    }

    @Override
    public void onStarted(List<Integer> ports) {
        // runs once every port is bound; /mockserver/ready stays not-ready until it returns
    }

    @Override
    public void stop() {
        // runs when MockServer stops
    }
}

Every method except name() is optional. Extensions start in order of priority() (lowest first, default 0), then by name, and stop in the reverse order.

Seeding expectations

An extension that also implements org.mockserver.server.initialize.ExpectationInitializer has its expectations loaded when MockServer starts, after the configured initialisers:

public class SeedExtension implements Extension, ExpectationInitializer {

    @Override
    public String name() {
        return "seed";
    }

    @Override
    public Expectation[] initializeExpectations() {
        return new Expectation[]{
            new Expectation(request().withPath("/health")).thenRespond(response().withBody("ok"))
        };
    }
}
 

Serving your own control-plane routes

An extension that also implements org.mockserver.extension.AdminApiExtension answers every request under /mockserver/extensions/<name>/, where <name> is its name(). Use it to add your own operations next to MockServer's, for example to reload test data or report the state your extension keeps:

public class TestDataExtension implements Extension, AdminApiExtension {

    @Override
    public String name() {
        return "test-data";
    }

    @Override
    public HttpResponse handle(HttpRequest request, String subPath) {
        // PUT /mockserver/extensions/test-data/reload has subPath "/reload"
        if (subPath.equals("/reload")) {
            reload();
            return response().withStatusCode(200).withBody("reloaded");
        }
        return null; // answered 404
    }

    @Override
    public boolean isReadOnly(String method, String subPath) {
        return subPath.equals("/status"); // only /status can be called with the read role
    }
}

These routes are part of the control plane, so they are protected exactly like MockServer's own:

  • the same control-plane authentication (JWT, mTLS or OIDC) applies, so a caller without valid credentials gets 401 and your code is never called;
  • with controlPlaneAuthorizationEnabled, every route needs the role that may change state, GET included, unless isReadOnly returns true for it; a caller without the role gets 403. isReadOnly is only asked once the caller has been authenticated;
  • the same browser-origin check and CORS headers apply, and calls are recorded in the control-plane audit log when it is on.

Your code never runs on MockServer's network threads, so a slow route cannot hold up mocked responses:

  • at most extensionAdminMaxInFlight calls (default 32) run at once; a call beyond that gets 503 with Retry-After: 1, including a call your route makes back into MockServer while the limit is reached;
  • a call that has not answered within extensionAdminTimeoutMillis (default 30 seconds) gets 500, and your code is interrupted; what it returns afterwards is discarded. The call keeps its place in the limit until your code returns, so code that ignores the interrupt makes later calls get 503;
  • a call made while MockServer is stopping gets 503, and your code is not called;
  • an exception gets 500 with a correlation id that you can find in the MockServer log; the exception's message is not sent to the caller;
  • in a WAR your code runs on the servlet container's request thread, and in-process on the thread that called handle, with the same limit but no timeout.

Only the names of loaded extensions are taken. Any other path under /mockserver/extensions/ behaves as it did before, so an expectation for it still matches. An expectation for a path under a loaded extension's name no longer matches, and MockServer logs a warning at start-up for each such expectation it loads then.

Listening to what MockServer does

An extension can also implement one or more listener interfaces, like WireMock's ServeEventListener, StubLifecycleListener and GlobalSettingsListener:

InterfaceTold about
ServeEventListenerEach request MockServer answered: a mocked response, a forwarded response or the not-matched response, with the request, the response, the id of the expectation that answered it and when. Bodies are cut to maxLoggedBodyBytes when that is set; headers are not redacted. Load-test traffic MockServer generates itself is not reported.
ExpectationLifecycleListenerEach expectation added, updated or removed, and why: API, FILE_INITIALISER, CLASS_INITIALISER, FILE_WATCHER, EXHAUSTED (no matches left), EXPIRED (its time to live passed), EVICTED (to stay within maxExpectations) or CLUSTER (another node changed it).
SettingsListenerEach PUT /mockserver/configuration, after it has been applied. Calling Configuration setters in your own code does not notify it.
public class TrafficRecorder implements ServeEventListener, ExpectationLifecycleListener {

    @Override
    public String name() {
        return "traffic-recorder";
    }

    @Override
    public void onServed(ServeEvent event) {
        // event.disposition(), event.request(), event.response(), event.expectationId()
    }

    @Override
    public void onChange(ExpectationChange change) {
        if (change.type() == ExpectationChange.Type.REMOVED && change.cause() == ChangeCause.EXHAUSTED) {
            // an expectation has used up its matches
        }
    }
}

Each listener extension gets a thread of its own, so a listener may block or do slow work without slowing MockServer down. Expectation changes wait in a queue in the order MockServer made them; when a listener falls too far behind, further events for it are dropped (see extensionListenerQueueSize and extensionListenerMaxBytes) and counted in the mock_server_extension_listener_dropped_total metric. A dropped event never affects the event log or verification. An exception thrown by a listener is logged once and counted in mock_server_extension_errors_total, and later events are still delivered. When MockServer stops, it delivers what is still queued for up to stopDrainMillis before stopping the extensions.

An expectation that runs out of matches is reported as soon as the response that used its last match completes. An expectation whose time to live passes with no traffic is reported when a later request or a retrieve next finds it. The expectation in a change is MockServer's own, not a copy, so read it but do not change it.

 

Template helpers

An extension that also implements org.mockserver.extension.TemplateHelperProvider adds its own helpers to response and forward templates, under ext.<extension name>. Velocity and JavaScript templates call the methods of a public interface you choose; Mustache templates use a section helper, which receives the section after it has been rendered:

public class AcmeHelpers implements TemplateHelperProvider {

    public interface Strings {          // must be a public interface
        String upper(String value);
    }

    @Override
    public String name() {
        return "acme";
    }

    @Override
    public Map<Class<?>, Object> helpers() {
        // Velocity: $ext.acme.Strings.upper($request.path)
        // JavaScript: ext.acme.Strings.upper(request.path)
        return Map.of(Strings.class, (Strings) value -> value.toUpperCase());
    }

    @Override
    public Map<String, MustacheHelper> mustacheHelpers() {
        // Mustache: {{#ext.acme.upper}}{{request.path}}{{/ext.acme.upper}}
        return Map.of("upper", section -> section.toUpperCase());
    }
}

How helpers run:

  • Only a response template (httpResponseTemplate) or a forward template (httpForwardTemplate) can call a helper. Any other template that calls one (a webhook, a secondary action, a delay, a templated file body, a stream, a load scenario or the template dry run) fails with an error saying so.
  • Each call runs on a helper thread of its own, never on a thread that handles network traffic, so a slow helper cannot hold up other requests.
  • All the helper calls one template makes share one time budget, extensionHelperTimeoutMillis (default 1 second). A call still running when it is used up is interrupted and the template fails, like any other failing template.
  • At most extensionHelperMaxInFlight calls (default 32) run at once; a call over that limit fails its template at once. A helper cannot call another helper.
  • Helpers work the same over HTTP/1.1, HTTP/2 and HTTP/3.

Give helper methods string, number or boolean parameters. A JavaScript object or array passed to a helper cannot be read on the helper's thread, so pass it as JSON.stringify(...) and parse it in the helper. When a helper throws, the template's error names only the exception's type, so a client never sees what the exception says; the MockServer log has the full exception.

Keep helpers short and non-blocking. Anyone who can create an expectation can call them, so a helper must not return an object that exposes reflection or class loading, which would get round velocityDisallowClassLoading and the JavaScript class allow-list: return strings, numbers, booleans or plain data.

Loading extensions

Name the extension classes in the extensions property, as a comma-separated list, and put their JARs on MockServer's classpath.

Command line — java -jar ignores -cp, so start MockServer with its main class:

java -cp mockserver-netty-jar-with-dependencies.jar:ext/* org.mockserver.cli.Main \
  --port 1080 \
  --extensions com.example.AuditExtension,com.example.SeedExtension

System property, environment variable or property file:

-Dmockserver.extensions=com.example.AuditExtension
MOCKSERVER_EXTENSIONS=com.example.AuditExtension
mockserver.extensions=com.example.AuditExtension

Docker — every MockServer image adds every JAR in /extensions to the classpath, so mount a folder of extension JARs there, read-only, and set the property. This works the same in every image variant, including -graaljs, -clustered and -aot, and keeps the images' fast start-up. Use /extensions rather than /libs: the -graaljs and -clustered images ship their own JARs in /libs, so mounting over it breaks them.

docker run -v "$(pwd)/ext:/extensions:ro" -e MOCKSERVER_EXTENSIONS=com.example.AuditExtension -p 1080:1080 mockserver/mockserver

Helm — put the JARs in any Kubernetes volume (a ConfigMap, a Secret, a PersistentVolumeClaim, ...) and the chart mounts it read-only at /extensions:

extensions:
  classes: "com.example.AuditExtension"
  volume:
    configMap:
      name: mockserver-extensions

Embedded Java — pass classes or suppliers. Each server you start gets its own instances, even when two servers share one Configuration:

ClientAndServer mockServer = ClientAndServer.startClientAndServer(
    Configuration.configuration().extensions(AuditExtension.class),
    1080
);

Spring — set the property on the test or on each named instance; each instance loads only the extensions it names:

@MockServerTest("mockserver.extensions=com.example.AuditExtension")

@MockServerInstance(name = "orders", properties = "mockserver.extensions=com.example.AuditExtension")

WAR — put the JARs in WEB-INF/lib and set the system property or mockserver.properties. onStarted is called once, when the servlet is created, with an empty list of ports.

In-process — pass them to new InProcessMockServer(configuration().extensions(AuditExtension.class)). They start when the instance is created and stop when it is closed. onStarted gets an empty list of ports, admin routes are reached by passing the request to handle and run on the calling thread with no timeout, and a SettingsListener is never called, because PUT /mockserver/configuration is not available in-process.

To also load extensions listed in META-INF/services/org.mockserver.extension.Extension files on the classpath, turn on extensionScanning. It is off by default, so only the extensions you name are loaded.

When an extension fails

MockServer refuses to start, and the error names the extension, if:

  • an extension class cannot be found, does not implement Extension, or has no public no-argument constructor;
  • two extensions have the same name, or a name is not lower-case letters, digits and -;
  • start or onStarted throws, or does not return within extensionStartTimeoutMillis (default 30 seconds);
  • a template helper is not a public interface with an implementation of it, two helpers of one extension share an interface name, or a Mustache helper key is not letters, digits, _ or -;
  • an extension that seeds expectations throws from initializeExpectations. This is stricter than initializationClass, which only stops start-up when failOnInitializationError is set;
  • a file MockServer is set to write would land in the folder an extension was loaded from: persisted expectations (persistExpectations), persisted recorded expectations (persistRecordedExpectations), persisted recorded requests (persistRecordedRequestsToDisk), the audit log (auditLogFile) or the memory-usage CSV files (outputMemoryUsageCsv). Write them somewhere else, such as a separate volume. For an extension JAR this means the JAR's own folder, for example /extensions; for a folder of classes it means anywhere inside it.

The extensions that had already started are stopped, in reverse order, and nothing else is left running, except the thread of an extension call that did not return in time: it is interrupted, and a warning says it may still be running. An exception thrown from stop is logged and the other extensions still stop.

GET /mockserver/configuration shows the configured extension names; a PUT that changes them is ignored with a warning in the log.
