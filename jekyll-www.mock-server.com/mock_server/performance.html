What makes MockServer scale

The throughput and latency above come from a few deliberate design choices:

  • Netty — an asynchronous, event-driven network framework. A small pool of event-loop threads handles many thousands of concurrent connections without a thread per request, which is what keeps latency flat as load rises. Where the OS supports it, MockServer uses Netty's native epoll transport for lower per-request overhead than the portable NIO transport.
  • Candidate-matching index — instead of testing a request against every expectation in turn (an O(n) scan), MockServer indexes expectations so each request is compared only against a small candidate set. This is why matching cost stays nearly flat as expectations grow (chart above). It falls back to a scan only for expectations that cannot be indexed (for example, fully regex-based paths).
  • LMAX Disruptor — a high-performance inter-thread messaging library used to record events (request log, recorded requests) and logging off the request path, so capturing state does not block responses.
  • Forward-proxy connection pooling — when MockServer forwards or proxies requests upstream, connections are pooled and reused, avoiding per-request connection setup and ephemeral-port exhaustion under sustained forward load.
  • Fail-fast matchers — request matching short-circuits on the first non-match, so non-matching expectations are rejected as cheaply as possible.
  • Bounded in-memory log — the request/event log is a fixed-size ring buffer (maxLogEntries), so memory stays bounded under sustained load. For long-running, high-throughput instances this is the most important thing to tune — see memory & troubleshooting below.
  • ScheduledThreadPoolExecutor — response delays are scheduled rather than blocking a thread, so simulated latency does not consume the event-loop threads.

Most of these are configurable — thread-pool sizes, native transport, and matcher behaviour are covered under scalability configuration below.

 

How MockServer is performance tested

The numbers on this page are produced by a performance suite (mockserver-performance-test/) built around k6 for load generation and the JMH microbenchmark harness for component-level measurement. A few principles make the results trustworthy:

  • Open-model load (no coordinated omission). Load is generated at a fixed arrival rate rather than by a fixed number of looping clients. This avoids coordinated omission — the measurement artefact where slow responses hide further slow responses — so the reported latency is what a real caller would experience under that offered load.
  • A ladder of test types, each answering a different question:
    • load — steady throughput at a target rate; the CI pass/fail gate.
    • sweep — steps the arrival rate up a ladder to find the throughput/latency knee (the first chart).
    • regression / growth — fixed-rate latency per behaviour (match, forward, template, large body) over HTTP and HTTPS+HTTP/2, plus a check that latency and memory do not creep upward over a run.
    • microbenchmarks — JMH measurement of matching time and allocation per request, including the candidate-index scaling sweep.
    • stress and soak — scenarios included in the suite for you to run on demand: stress pushes past the knee to find the breaking point, soak holds sustained load to surface memory growth and leaks. The figures on this page come from the load, sweep, regression/growth and microbenchmark runs above.
  • Reproducible and core-pinned. Measurement runs on a dedicated CI machine with the server, upstream and load generator pinned to separate CPU cores so they do not steal cycles from each other — the single biggest factor in number quality. Every chart is regenerated from the pipeline's JSON output.
    • {% if rule %}
  • Enough load generators. One k6 process cannot drive a six-core MockServer to its limit{% if sk.headline.healthy_ceiling_rps_display %} — on its own it runs out at about {{ sk.headline.healthy_ceiling_rps_display }} requests/sec{% endif %}. The headline run therefore drives one MockServer from {{ figures.source.k6_processes | default: "four" }} k6 processes on the machine's other CPU socket and merges their measurements, so the ceiling is no longer set by one load generator running out.
    • {% endif %}
  • Automated regression detection. Each run is stored and compared against a rolling baseline using a robust median + MAD test, so a real slowdown is flagged without false alarms from run-to-run noise.

Why there are two p99 columns. The load generator, k6, is a Go program and pauses briefly for its own garbage collection. A request that completes around such a pause is timed late by the client even when MockServer answered on time, and at high rates those pauses set most of the client-observed tail. The first p99 column counts every second of the step. The second leaves out each second in which any of the load generators was collecting, and the second after it; the “seconds counted” column says how many seconds remain. The {{ figures.headline.p99_max_ms | default: 10 }} ms bound reads the second column.{% if rule.unmasked_ceiling_rps_display %} Judged on the first column, this run's ceiling would be {{ rule.unmasked_ceiling_rps_display }} req/s.{% endif %} It is still a client-observed figure and a sample of the step, not a measurement of MockServer free of every outside effect: MockServer still served the burst that follows each pause. The second column still rises as the rate nears the ceiling, and this test does not show how much of that remaining tail is MockServer's.

The recorded-request store is not application logging. The received-request and response entries it holds — the ones a verify reads — are stored whatever the log level, so lowering the level does not shrink them. It does drop the per-expectation match/did-not-match diagnostics, which are only produced at INFO or finer, so on a workload with many expectations a lower level still helps. It is the store behind request verification (verify), the retrieveRecordedRequests API, and the dashboard — it fills regardless of log level, and reaching for disableLogging=true when you see latency spikes will not help.

Levers for heap use:

  • Bound the recorded-request store — lower maxLogEntries or set a byte budget with maxEventLogSizeInBytes if you do not need the full verification history. This directly reduces the heap pinned by the store. The trade-off: fewer entries available for verify calls and the dashboard history.
  • Give the JVM more heap — a larger -Xmx means the same number of entries consumes a smaller fraction of available heap, reducing collection frequency. The trade-off: higher memory commitment for the container or host.

Tuning for your workload

The defaults are tuned for general use. For sustained high throughput, large payloads, or long-running instances, the most effective levers are memory/log sizing and a few scalability settings — covered in detail below. The single most common cause of an instance slowing down over time is the in-memory request log filling the heap; see memory & troubleshooting.

 

Concurrent connection limits are set by the OS and the JVM, not by MockServer

If you are load-testing MockServer, or running it in front of many long-lived keep-alive clients, the ceiling you hit first is almost never MockServer's. It is one of two operating-system limits, and on macOS the first of them is invisible — the JVM quietly overrides what you set. Both apply to the machine running MockServer and the machine driving load at it, independently: whichever hits its limit first is the one that fails.

1. File descriptors — one per connection

Every established TCP connection consumes a file descriptor. The JVM does not simply inherit the limit your shell reports, and what it does instead is the opposite on the two platforms:

PlatformWhat the JVM does by defaultWith -XX:-MaxFDLimit
macOS Caps the limit at 10,240 (the BSD OPEN_MAX), however high ulimit -n reads. A shell reporting 60,000 still gives a JVM 10,240. It also raises a lower limit up to 10,240. Uses the shell's soft limit unchanged — 60,000 stays 60,000, and 2,048 stays 2,048.
Linux Raises the soft limit to the hard limit automatically. A service started with a soft limit of 1,024 and a hard limit of 1,048,576 gets 1,048,576 — no flag needed. Makes things worse. Disables that automatic raise, leaving the soft limit: 1,024.

So the correct action is different on each platform, and the flag is not a portable "more file descriptors" switch:

  • macOS — you need both. Raise the shell limit ulimit -n 65536 and start the JVM with -XX:-MaxFDLimit. The flag alone gives you whatever the shell had; the shell alone is ignored above 10,240.
  • Linux — do not pass the flag. Make sure the hard limit is high and the JVM will take it: LimitNOFILE=1048576 in a systemd unit, --ulimit nofile=1048576:1048576 for docker run, or the container runtime's default in Kubernetes (usually already high).

How the limit announces itself: the JVM cannot create the socket at all, so you see Too many open files, or from Netty ChannelException: Unable to create Channel from class ... NioSocketChannel. That is a resource limit on the machine reporting it — not MockServer refusing the connection, and not the network.

2. Ephemeral ports — a limit on the client side only

A connection is identified by (source IP, source port, destination IP, destination port). A load generator opening many connections to one MockServer draws a source port from the ephemeral range for each, so the range size caps how many it can hold at once:

PlatformDefault rangeUsable connectionsHow to widen it
macOS 49152–65535 ~16,000 sudo sysctl -w net.inet.ip.portrange.first=32768 (about 32,700 ports, matching Linux's default start)
Linux 32768–60999 ~28,000 sysctl -w net.ipv4.ip_local_port_range="10000 65535", or docker run --sysctl net.ipv4.ip_local_port_range="10000 65535"

Do not lower the start of the range too far. Ports below it are where fixed services bind, and an ephemeral connection that happens to take one can stop a service binding it later. Starting at 32768 matches Linux's own default and stays clear of the registered-port range.

These sysctl -w changes do not survive a reboot. To make one permanent, add it to /etc/sysctl.conf on macOS, or a file under /etc/sysctl.d/ on Linux. A docker run --sysctl flag applies to that container only, and needs repeating for each run.

Which of these we verified: the file-descriptor behaviour in the table above was measured on both platforms, as were the default port ranges and the connection counts below. The Linux sysctl/--sysctl change was tested and takes effect. The macOS sysctl change is the documented mechanism but we have not measured it, because it is a system-wide change to a developer machine.

Giving MockServer more ports does not help. It is tempting to assume that spreading connections over several server ports gives each its own source-port space. On macOS it does not — the range is global to the client, and measurement confirms it: 15,511 connections to one server port, 15,609 spread over four, a difference of 1%. To exceed the range you need more client source addresses (extra loopback aliases, or more load-generator machines), not more server ports — and that is measured, not predicted: driving from two source addresses carried 16,000 connections, past the 15,511 single-address wall. Capacity is per source address even though the ephemeral port counter is global, so each address contributes its own range.

Connections arriving in a burst need accept-queue room. A third OS limit sits beside file descriptors and ephemeral ports, and it announces itself differently from both. While MockServer accepts connections, the kernel parks completed handshakes in a queue whose depth is mockserver.soBacklog (default 1024), capped by net.core.somaxconn on Linux or kern.ipc.somaxconn on macOS. When that queue fills, the kernel does not refuse the connection — it silently drops the handshake packet and the client retransmits after its initial timeout, about one second on Linux. The symptom is therefore a median latency of roughly a second with zero errors, which looks like a slow server rather than a limit being hit. Raise both the property and the OS value together; in Docker the container has its own somaxconn, so --sysctl net.core.somaxconn=16384 is needed as well as the host setting. This only affects connection establishment: traffic over existing keep-alive connections never touches the queue.

Closed connections keep their port for a while. A socket you close sits in TIME_WAIT holding its source port — 30 seconds on macOS (twice the 15-second net.inet.tcp.msl), 60 seconds on Linux by default. So a test that opens 10,000 connections, closes them, and immediately opens 10,000 more is asking for 20,000 ports. Linux can reuse those sockets for new outbound connections: net.ipv4.tcp_tw_reuse defaults to 2, which enables reuse for loopback traffic only — set it to 1 to enable it for all traffic. macOS has no equivalent, so there you simply wait it out between runs.

How this limit announces itself: Can't assign requested address / BindException. Note that it looks nothing like the file-descriptor error above, and the fix is entirely different — if you see one and apply the other's remedy, nothing will change.

What we measured

On an Apple M3 Max laptop (macOS, Zulu JDK 21), driving a MockServer in a second JVM on the same machine: with the JVM's default file-descriptor behaviour the driver stopped at 9,977 connections — the 10,240 cap, not MockServer. (The few hundred missing are the descriptors the JVM and the OS already hold for their own use, so the usable ceiling always sits a little below the raw limit.) With -XX:-MaxFDLimit on both JVMs it reached 15,511, stopping at the ephemeral port range instead. Holding 16,000 idle keep-alive connections — reached by spreading them over two source addresses — request latency on a separate connection was indistinguishable from the same measurement with no connections held — run-to-run variation exceeded any effect of the held connections. MockServer itself was not the limiting factor at any point; both ceilings belonged to the machine.
