When an expectation does not match a request, MockServer returns a 404 response. This page explains how to diagnose and fix matching issues.

 

Debugging Checklist

Follow these steps in order when a request is not matching:

If the request was served, but by a different expectation from the one you expected, or you already have its correlation ID, go straight to explaining a specific request: it names the expectation that wins and why each higher-priority one lost.

1. Is the expectation active?

Expectations expire after their configured times limit or timeToLive. Retrieve active expectations to confirm yours is still present:

3. Check the match failure reason

MockServer logs an EXPECTATION_NOT_MATCHED event for every expectation that was compared. Each event includes a because section explaining which fields matched and which did not:

curl -X PUT "http://localhost:1080/mockserver/retrieve?type=LOGS"

When a request matches nothing and more than 1,000 expectations are stored, MockServer compares it with the expectations that share its method and path (plus any whose method or path is not a plain value) and with at most 1,000 others, in the order it would serve them, so a flood of unmatched requests stays cheap. The log then has an event only for the expectations it compared, and the closest-match entry ends with only N of M expectations were checked, so a closer one may exist.

In the dashboard UI, look for log entries with the pink/rose colour. Click the ... to expand the "because" section, which shows each field result colour-coded green (matched) or red (didn't match).

4. Enable full match diagnostics

By default, MockServer stops comparing fields at the first mismatch (matchersFailFast=true). To see all mismatching fields at once, disable fail-fast:

ConfigurationProperties.matchersFailFast(false);
# System property
-Dmockserver.matchersFailFast=false

# Environment variable
MOCKSERVER_MATCHERS_FAIL_FAST=false

This shows every field that does not match in a single log entry, making it much easier to identify all issues at once rather than fixing them one at a time.

5. Look for the closest match

When no expectation matches, MockServer logs a closest match summary showing which expectation was most similar to the request and how many fields matched (e.g., "matched 14/16 fields"). This immediately tells you which expectation to investigate.

 

Common Pitfalls

These are the most frequent reasons expectations fail to match:

Trailing slash in path

A path of /api/users does not match /api/users/. Ensure your expectation path matches exactly, or use a regex:

// Exact match - will NOT match "/api/users/"
.withPath("/api/users")

// Match with or without trailing slash
.withPath("/api/users/?")

MockServer will show a HINT in the match failure when it detects a trailing slash mismatch.

Content-Type charset mismatch

Many HTTP clients send Content-Type: application/json; charset=utf-8 but expectations often specify just application/json. This is a header value mismatch.

Solutions:

  • Include the charset in your expectation: .withHeader("Content-Type", "application/json; charset=utf-8")
  • Use a substring header matcher
  • Omit the Content-Type header from your expectation (unspecified headers match anything)

MockServer will show a HINT when it detects this pattern.

JSON body matching semantics

By default, JSON body matching uses ONLY_MATCHING_FIELDS mode:

  • Extra fields in the request body are ignored (the expectation is a subset match)
  • Missing fields (a field specified in the matcher but absent from the request body) cause a failure
  • Array order does not matter
  • Extra array items are ignored

If you need an exact match, use STRICT mode:

// Subset match (default) - extra fields OK
.withBody(json("{\"name\": \"foo\"}", MatchType.ONLY_MATCHING_FIELDS))

// Strict match - no extra fields allowed
.withBody(json("{\"name\": \"foo\"}", MatchType.STRICT))

Regex metacharacters in paths

Paths are matched as regular expressions. Characters like ., *, +, ?, (, ), [, { have special meaning in regex.

For example, /api/v1.0/users will also match /api/v1X0/users because . matches any character. Use \. for a literal dot:

// This matches "/api/v1X0/users" too
.withPath("/api/v1.0/users")

// This only matches "/api/v1.0/users"
.withPath("/api/v1\\.0/users")

MockServer will show a HINT when it detects unescaped dots in paths.

Header name case sensitivity

HTTP header names are matched case-insensitively (per HTTP spec), but header values are case-sensitive. For example:

// Header name "content-type" matches "Content-Type" - OK
// Header value "Application/JSON" does NOT match "application/json"
.withHeader("Content-Type", "application/json")

Query parameter encoding

Query parameters are decoded before matching. ?name=hello%20world is matched against the decoded value hello world:

// Matches ?name=hello%20world and ?name=hello+world
.withQueryStringParameter("name", "hello world")

Body type confusion

Using the wrong body matcher type is a common mistake:

// This is an EXACT string match - entire body must match this text exactly
.withBody("{\"name\": \"foo\"}")

// This is a JSON subset match - only specified fields must be present
.withBody(json("{\"name\": \"foo\"}"))

// This is a regex match
.withBody(regex(".*foo.*"))

If your JSON body isn't matching, check that you are using json() and not a plain string body matcher.

 

Reading the "because" Output

When a request does not match an expectation, the log entry includes a "because" section. Here is an annotated example:

method matched                        ← GET matched GET
path didn't match:                    ← path comparison failed

  string or regex match failed        ← the matcher type used
  expected: /api/users                ← what the expectation specified
  found: /api/user                    ← what was in the request
HINT: trailing slash mismatch ...     ← actionable suggestion (when applicable)
body matched                          ← body was not checked (no body matcher)
headers matched                       ← all expected headers were found
cookies matched                       ← all expected cookies were found

Fields are listed in matching order. When matchersFailFast=true (default), only fields up to and including the first failure are shown. Set matchersFailFast=false to see all fields.

 

Debugging Configuration Properties

Property Default Description
matchersFailFast true When true, matching stops at the first non-matching field. Set to false to see all mismatching fields in a single log entry.
detailedMatchFailures true When true, match failure log entries include detailed explanations of why each field did not match (expected vs actual values).
logLevel INFO At INFO (default), all match results are logged with full detail. Set to TRACE for internal matcher-level diagnostics — see Debugging Issues → Logging Levels for how to set the log level and what each level reports.

For full configuration details, see the Configuration page.

Suggested Fixes for Unmatched Requests

When a request got a 404 because an expectation was almost right, MockServer can suggest the smallest change to that expectation that would make it match. Nothing is changed until you choose to apply the fix.

In the dashboard: open Explain Unmatched Requests, select Preview Fix next to one of the closest expectations, check the changes and the request matcher before and after, then select Apply Fix. Apply re-reads the expectation first: if anything the fix changes was edited since the explanation was computed, the fix is refused rather than overwriting the edit.

Over REST: add "suggestFixes": true to the PUT /mockserver/explainUnmatched body. Each of the five closest non-matching expectations then carries a suggestedFix:

curl -X PUT "http://localhost:1080/mockserver/explainUnmatched" \
  -H "Content-Type: application/json" \
  -d '{ "limit": 5, "suggestFixes": true }'
"suggestedFix" : {
  "patch" : [
    { "op" : "test", "path" : "/httpRequest/path", "value" : "/api/order" },
    { "op" : "replace", "path" : "/httpRequest/path", "value" : "/api/orders" },
    { "op" : "test", "path" : "/httpRequest/headers/X-Tenant", "value" : [ "blue" ] },
    { "op" : "replace", "path" : "/httpRequest/headers/X-Tenant", "value" : [ "green" ] }
  ],
  "patchedFields" : [ "path", "headers" ],
  "unpatchedFields" : [ ],
  "matchesAfterPatch" : true
}
  • patch is a standard JSON Patch of the expectation as PUT /mockserver/retrieve?type=active_expectations returns it. Each change is guarded by a test of the current value (for an addition, of the object it adds to), so applying it fails if anything it changes has been edited since; edits to other parts of the expectation are kept. To apply it yourself, patch the retrieved expectation and send the result to PUT /mockserver/expectation, which updates the expectation with the same id.
  • Only the fields that differ are changed. For headers, query parameters and cookies, only the entries the request contradicts are changed (or removed if the request does not send them). For a JSON body matched on its listed fields (the default), only the fields the request contradicts are changed, fields the request lacks are removed, and placeholders such as ${json-unit.any-string} are kept; a STRICT JSON body, or any other kind of body, is replaced by the request's body.
  • unpatchedFields lists anything that could not be fixed automatically and why — for example a client certificate or JWT matcher, a body the log kept only part of (maxLoggedBodyBytes), or a value the log redacts (redactSecretsInLog), which is never copied into a patch.
  • matchesAfterPatch says whether the patched expectation matches the request. When it is false, the fields in unpatchedFields still need editing by hand.

A suggested fix makes the expectation match this request: replacing a regex path or a placeholder value with the literal value from the request can make it narrower than you intended, so check the preview before applying.

AI assistants can ask for the same fixes through the MCP suggest_expectation_fix tool.

 

Retrieving Logs by Correlation ID

Every incoming HTTP request is assigned a unique correlation ID. All log entries for that request's lifecycle (received, match attempts, response) share this ID. This is invaluable when debugging a specific request among many — you can isolate exactly what happened.

Finding the Correlation ID

The correlation ID appears in:

  • Dashboard UI — as a small chip on grouped log entries (click to copy)
  • Log text — in the prefix of each log message
  • Typed log entries — as the correlationId field when using format=LOG_ENTRIES

Explaining Why a Request Matched One Expectation and Not Another

When a request was served by the wrong expectation, or by none, PUT /mockserver/explain?correlationId=<id> tells you why. It takes the recorded request with that correlation ID and checks it again against your current expectations, in the same order MockServer uses when a request arrives (highest priority first, then oldest first). It returns:

  • matchedExpectation — the expectation that would serve the request now (absent if none would; closestExpectationId then names the closest one)
  • skippedExpectations — every expectation checked before it, each with a reason, a plain-language explanation and, for field differences, the same differences and remediation hints that explainUnmatched returns
  • shadowedExpectations — lower-priority expectations that also match but are never reached
  • atArrival — how the request was actually handled when it arrived (MATCHED with the expectation ID, NO_MATCH, FORWARDED_WITHOUT_EXPECTATION, RESPONDED_WITHOUT_EXPECTATION or UNKNOWN), and sameOutcomeAsAtArrival. When the request was forwarded and the forward failed (MockServer answered 502), atArrival.forwardFailure gives the reason; the outcome is then MATCHED with the forward expectation's ID, or FORWARDED_WITHOUT_EXPECTATION if the request was proxied without an expectation
  • expectationsChangedSince — true if any expectation was added, changed or removed since the request arrived
ReasonWhy the expectation was passed over
FIELDS_DIFFERThe request differs on one or more fields (method, path, headers, body, …)
NOT_OPERATORThe expectation's request matcher is wrapped in not(...) and the request matches everything inside it, so the expectation excludes this request
NAMESPACEThe expectation belongs to a different namespace from the request
INACTIVEIts Times are used up or its time to live has expired
SCENARIO_STATEIt needs its scenario to be in a different state from the current one
PERCENTAGEIt matches, but is only served for a percentage of requests
CONVERSATIONThe request matches, but its LLM conversation does not

The answer is worked out again when you ask, not recorded when the request arrived, so it costs nothing on normal requests. This also means it reflects the expectations, scenario states and remaining Times as they are now: an expectation limited to once() that served the request will usually show as gone (atArrival.expectationStillStored is false). If the request body was cut short in the log by maxLoggedBodyBytes, request.bodyTruncated is true and body matching is checked against the shortened copy. Request values in the output are redacted in the same way as the log. At most 500 expectations are checked; truncated says when that limit was reached. A correlation ID that is not in the log (never received, cleared, or dropped once maxLogEntries was reached) returns 404.

In the dashboard, each group of log messages for a request has an Explain button next to its correlation ID, which shows the same answer: the matched expectation, the skipped ones with their reasons and differences, and the shadowed ones. Every client has a typed method for it: explain in Java, JavaScript, Python, Ruby, Rust and PHP, and Explain in Go and .NET.

Plain-language summary from your own LLM (optional)

If you have configured a runtime LLM backend and turned on llmExplainNarrationEnabled (off by default), add narrate=true to PUT /mockserver/explain or PUT /mockserver/explainUnmatched to get a short summary in plain words, for example "expectation gold-tenant wants X-Tenant: gold but the request sent silver, so the catch-all served it":

curl -X PUT "http://localhost:1080/mockserver/explain?correlationId=abc-123-def-456&narrate=true"

The response is the same as without narrate, with one extra narration field:

"narration": {
  "available": true,
  "aiGenerated": true,
  "label": "AI-generated by the configured LLM and can be wrong; the other fields of this response are the deterministic facts",
  "provider": "OPENAI",
  "model": "gpt-4o-mini",
  "text": "..."
}
  • Off unless you ask, twice. Nothing is sent to an LLM unless whoever runs MockServer sets llmExplainNarrationEnabled=true (for example -Dmockserver.llmExplainNarrationEnabled=true or MOCKSERVER_LLM_EXPLAIN_NARRATION_ENABLED=true) and the caller adds narrate=true; a backend configured for other features is not enough. Nothing is ever sent while a request is being served or answered with a 404.
  • The facts stay authoritative. The summary is written by an LLM and can be wrong, so it is labelled as AI-generated; every other field is MockServer's own deterministic answer.
  • Credentials are removed first. Before the explanation is sent, credential values from the request and your expectations (authorization headers, cookies, API keys, tokens, passwords and other credential fields, JWTs and URL passwords) are replaced with ***REDACTED***, whether or not redactSecretsInLog is on, and long values are shortened.
  • Never an error. With narration turned off, no LLM backend configured, or when the LLM fails, returns nothing or does not answer within llmRequestTimeoutMillis plus two seconds, you still get the full explanation, and narration has "available": false and a reason. At most two summaries are produced at once; a third request is answered straight away with the reason.
 

Linting Expectations

Some expectations can never match, however the request is sent: one evaluated earlier catches every request it would match, a path is missing its leading /, or times allows 0 matches. Lint finds these before you spend time debugging a 404. It is advisory: it never rejects or changes an expectation.

Lint runs in four places:

  • When you create expectations — PUT /mockserver/expectation (and every client's create or upsert call) still stores the expectations, but when a quick check finds a problem the response carries an x-mockserver-lint-warnings header with the number of problems, and each one is written to the log as a WARN. This quick check looks at each expectation on its own; it does not look for shadowing.
  • When an initialisation file loads — expectations loaded from initializationJsonPath (--init) are checked once each time the file loads, at start-up and again on every reload when the file is watched (--watch). Every expectation is still loaded; any problems, including an expectation shadowed by one earlier in the same file and a later entry that repeats an id (the load ignores it and keeps the first), are written to the log as one WARN that names the file and lists the first 20 problems; a reload that finds the same problems does not repeat them. An expectation without an id is named by its method and path.
  • On demand — PUT /mockserver/lint with an empty body checks all your active expectations, including for shadowing. Send expectations in the body (one, or an array) to check them without storing them. It only reads, so a client with the read role may call it.
  • In the dashboard — the Lint button on the dashboard's Active Expectations panel lists the same findings, and clicking an expectation id (including the one that shadows another) opens it in the Mocks composer. Creating an expectation in the Mocks composer, importing Expectation JSON, registering a generated stub, capturing a request as a mock or applying a suggested fix shows a Lint Warnings badge when the create found problems.
  • From the command line — mockserver lint expectations.json checks expectation files with no server running (see command line subcommands).
  • From an AI assistant — the MCP lint_expectations tool runs the on-demand check.
RuleWhat it finds
SHADOWEDAn expectation evaluated earlier (higher priority, or the same priority and created earlier) matches every request this one matches and never runs out, so this one is never used. Give this one a higher priority, or make the other more specific.
TIMES_ZERO, TIME_TO_LIVE_ZERO, PERCENTAGE_ZEROtimes, timeToLive or percentage is 0, so the expectation is never served
UNREACHABLE_RESPONSESA list of responses that times never reaches: with times of 2, the third response is never sent
PATH_MISSING_LEADING_SLASHusers/1 instead of /users/1
PATH_INCLUDES_SCHEME_AND_HOSThttps://api.example.com/users: the path is matched without the scheme and host
PATH_INCLUDES_QUERY_STRING/search?q=shoes: use queryStringParameters instead
PATH_GLOB_WILDCARD/api/*: paths are regular expressions, so use /api/.*
PATH_TEMPLATE_WITHOUT_PATH_PARAMETERS/users/{id} without pathParameters, which matches only the literal text {id}
METHOD_TYPO, HEADER_NAME_TYPOA method or header name close to a standard one, such as GTE for GET, Authorisation for Authorization or content_type for Content-Type
STRICT_JSON_BODY_WITH_ARRAYSInformation only: STRICT JSON matching of a body with arrays needs the same order and no extra items
INVALID_EXPECTATION, DUPLICATE_IDWhen checking expectations you send or files: an entry that would be rejected, or two entries with the same id, only one of which is kept: in expectations you send, the last; in files, the first in each file, with a file checked later replacing an earlier one, as loading initialisation files does

The shadowing check is careful: it reports an expectation only when it can prove the earlier one always wins, so it may miss some cases but does not report an expectation that can still be used. It never fetches an OpenAPI specification; OpenAPI entries in the body are skipped and counted. To keep it quick on very large expectation sets it compares at most 100,000 pairs and stops a regular expression that takes too long; shadowCheckTruncated is true when either limit was reached.

Typed Log Entry Retrieval

Instead of retrieving logs as plain text, you can retrieve structured LogEntry objects. This is useful for programmatic analysis — filtering by type, inspecting expectations, or building custom reports:

Each entry writes its request and response in full once, in httpRequest and httpResponse. Where the message and arguments refer to that same request or response, they show a short form instead: the method and path ("POST /orders") or the status code ("201"), so a large body is not repeated. For the same reason the expectation recorded for a proxied request is written without its request and response bodies. Read bodies from httpRequest and httpResponse; for the full rendered text of each message, retrieve the logs as plain text (format=JSON, the default). Before 9.0.0 the message and arguments repeated the full request and response.

LogEntry[] entries = mockServerClient.retrieveLogEntries(null);

LogEntry[] matchEntries = mockServerClient.retrieveLogEntries(
    request().withPath("/api/users")
);

// Deserialized entries include: type, logLevel, correlationId, epochTime,
// timestamp, port, expectationId, messageFormat, arguments, because.
// An argument that is the entry's own request or response arrives as a
// short string such as "POST /orders" or "201".
// Note: httpRequest, httpResponse, expectation, throwable are in the JSON
// but not deserialized (returned as null on the client).
for (LogEntry entry : entries) {
    System.out.println(entry.getType() + " at " + entry.getTimestamp());
}
