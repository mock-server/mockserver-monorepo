Security Notice: Java Base64 Decoding (CVE-2026-114938)

The MockServer Docker images from the release after 9.3.0 run a fixed Java runtime. If you run MockServer on your own Java on an x86-64 (Intel or AMD) machine, update that Java, or start it with -XX:-UseBASE64Intrinsics until you can. CVE-2026-114938 is a memory-corruption bug in how Java decodes Base64 on x86-64 processors that support AVX-512. It affects JDK 17.0.6 and later 17 updates, and JDK 21, 25, 26 and 27. MockServer decodes Base64 sent by clients (for example the base64Bytes field of an expectation, and gRPC-Web text bodies) before checking any credentials, so a MockServer that untrusted clients can reach is exposed. ARM64 machines (Apple Silicon, AWS Graviton) are not affected. Remote code execution has not been demonstrated.

Where you cannot update Java yet, the -XX:-UseBASE64Intrinsics option switches off the optimised Base64 encoder and decoder, including the one that contains the bug, so Java uses its ordinary ones, which give the same results. Security researchers recommend it as the workaround; the Java vendors have not confirmed it yet.

How you run MockServerWhat to do
Docker image or Helm chart, from the release after 9.3.0Nothing: every image runs a fixed Java runtime, Eclipse Temurin 27.0.1.1 on x86-64 (the -clustered image runs Temurin 21.0.13.1, because its clustering library does not yet run on newer Java). The ARM64 images, which the bug does not affect, run the newest Temurin build for ARM64; from the release after 9.4.0 that is the same 27.0.1.1 (and 21.0.13.1 for -clustered). The images no longer set -XX:-UseBASE64Intrinsics, and you do not need to add it.
Docker image, 9.3.0 or earlierUpgrade the image, or add the option to JAVA_TOOL_OPTIONS. Setting the variable replaces the image's default, so keep -XX:+UseZGC in it: -e JAVA_TOOL_OPTIONS="-XX:+UseZGC -XX:-UseBASE64Intrinsics" (for the -clustered image, keep its -XX:+ZGenerational too: -e JAVA_TOOL_OPTIONS="-XX:+UseZGC -XX:+ZGenerational -XX:-UseBASE64Intrinsics"; for the -aot image, -e JAVA_TOOL_OPTIONS="-XX:-UseBASE64Intrinsics"). With the Helm chart, set app.jvmOptions to the same value.
Executable JAR, WAR, Maven plugin, JUnit or Spring integration, the Java API, or mockserver-node without the binary bundleThese run on your own Java. Update it to a fixed build: Oracle JDK or Eclipse Temurin 17.0.21.1, 21.0.13.1, 25.0.5.1 or 27.0.1.1 (Temurin publishes these for x86-64 and ARM64), Amazon Corretto 17.0.21.1.2, or a fixed Azul Zulu build. Debian/Ubuntu OpenJDK have no fixed build yet. Until you can update, add -XX:-UseBASE64Intrinsics to the java command line, the application server's JVM options, or JAVA_TOOL_OPTIONS. From the release after 9.3.0, the Maven plugin's runForked goal and mockserver-node add it to the Java they start for you, but still update Java: in-process uses (JUnit, Spring, the Java API, the WAR) are not covered.
Binary bundle (client-library launchers and the VS Code extension), from the release after 9.3.0Nothing: the bundle's launcher starts Java with -XX:-UseBASE64Intrinsics after anything in MOCKSERVER_JAVA_OPTS, so neither that variable nor JAVA_TOOL_OPTIONS removes it (only _JAVA_OPTIONS would, as a deliberate override). mockserver-node and the VS Code extension, which start the bundled Java themselves, do the same from their matching releases. The bundle carries its own Java runtime, so upgrade again once a MockServer release ships a fixed one.
Binary bundle, 9.3.0 or earlierUpgrade, or set MOCKSERVER_JAVA_OPTS=-XX:-UseBASE64Intrinsics in the environment that starts it. You cannot update the bundle's Java runtime yourself.
