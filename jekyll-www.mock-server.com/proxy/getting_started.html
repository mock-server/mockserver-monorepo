As an in-path HTTP(S) proxy, MockServer records every request and response that flows through it — including HTTPS, which it can decrypt transparently with an auto-generated certificate. That means you can capture how a system really behaves and replay it as deterministic mocks without changing a line of application code: point your clients at MockServer, run your scenarios, then analyse, verify, or record-and-replay the captured traffic.

Inspecting AI agent traffic? If you want to see the HTTPS calls that Claude Code, OpenCode, or Python AI libraries send to LLM APIs and MCP servers, see Inspect AI Agent Traffic. It covers proxy setup, CA trust, and per-tool configuration for AI tools.

Proxying WebSockets? MockServer also proxies WebSocket connections. When a client opens a WebSocket (an HTTP Upgrade: websocket request) through MockServer and no matching WebSocket expectation exists, MockServer connects to the real upstream WebSocket server (over ws or wss), relays the handshake, and then relays messages in both directions until either side closes. The client receives the headers the upstream sent with its handshake response, such as Set-Cookie and the agreed subprotocol, except connection-level headers such as Keep-Alive and Proxy-*; WebSocket extensions such as compression are not negotiated through the relay. The relayed frames (text, binary, ping, pong, close) are recorded alongside the connection so you can inspect them with recorded requests and in the dashboard. The number of frames recorded per connection is capped by the webSocketProxyMaxRecordedFrames configuration property (default 1000; set to 0 to record only the handshake). This works whether the client connects to MockServer directly or uses it as its HTTP or SOCKS proxy (which is how browsers send ws:// and wss:// through a proxy), and covers HTTP/1.1 WebSocket upgrades over plain and TLS upstreams. A frame may be as large as maxRequestBodySize from the client (10 MiB by default) and maxResponseBodySize from the upstream (50 MiB by default).

 

Compressed responses. When MockServer forwards or proxies a request, it passes on the client's own Accept-Encoding header, keeping its order and q values but leaving out any compression MockServer cannot decompress (it decompresses gzip, deflate and zstd, and br when the Brotli4j library is on the classpath). That way the server receives the client's real preferences, and MockServer can still decompress whatever the server sends back, so recorded responses and the dashboard show readable bodies. A client that sends no Accept-Encoding has none sent on its behalf; if none of the client's choices can be decompressed, the server is asked for identity (no compression). A response compressed in one of those ways is passed back to the client decompressed, without its Content-Encoding header, and with any Vary header the server sent. Earlier versions always asked servers for gzip,deflate, whatever the client sent.
